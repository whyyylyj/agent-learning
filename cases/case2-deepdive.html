金融 DeepResearch 方案：10 个可以深挖的维度

怎么用：面试官追问"再深入一点"时，每个维度都是一条独立的防线——Struggle（真实困境）→ 拆解 → 调研测试 → 解决步骤 → 验证 → 效果 → 迭代中新问题与化解 → 业界对比 → 设计巧思。黄色高亮为待填真实数据。

维度 1 · 规划器：研究问题的子问题 DAG

深挖维度
价值点：deep research 的质量上限由规划决定：问题拆错，后面全白干。
Struggle
复杂研究问题直接丢给 agent 自由发挥，检索方向漂移、覆盖不全，且无法复现。
问题拆解
按'研究框架'拆解：主题 → 维度（规模/格局/驱动/风险）→ 每维度绑定数据源与工具；子问题间标注依赖关系形成 DAG。
调研与测试
调研 Plan-and-Execute、LLMCompiler（并行函数调用）与 Tongyi DeepResearch 的规划训练路线。
解决步骤
  • LLM 生成子问题 + 数据源映射
  • 依赖分析剔除循环
  • 并行调度无依赖子问题
  • 执行中发现缺口允许有限重规划（带预算）
验证思路
规划覆盖率人工评估（子问题并集是否回答原问题）；重规划次数监控。
达成效果
报告维度覆盖率从【占位】提升至【占位】。
迭代新问题
拆解过细导致任务爆炸 → 化解：子问题数量上限 + 合并同类项。
业界对比
LLMCompiler（并行函数调用学术工作）与 Anthropic 的编排者-执行者实践互相印证。
设计巧思
规划器的价值不是'拆得细'，是'拆成可并行、可验证的单元'。

维度 2 · 多源数据源接入与质量分层

深挖维度
价值点：金融数据的版权、合规与质量是生命线：来源本身就是证据等级。
Struggle
公告、研报、新闻、行情口径各异，新闻还常有转述错误，直接混用会互相污染。
问题拆解
按'权威度 × 新鲜度 × 结构化程度'给数据源分级，并为每源定义接入方式（API/解析）与更新频率。
调研与测试
调研 Wind/东方财富/同花顺的数据开放形态（MCP/Skills 趋势）与版权边界；确立接口优先原则。
解决步骤
  • 来源分级：公告/财报（一手）> 研报（二手分析）> 新闻（快讯）
  • 一手结构化数据走查询接口，文本走 RAG
  • 每条证据带来源等级与时间戳
验证思路
抽查证据的来源等级标注准确率；数据源故障演练（单源挂掉时报告降级策略）。
达成效果
数字类结论双源一致率达标【占位：__%】。
迭代新问题
部分数据源无正式 API → 化解：合规评估后用许可范围内的采集，或转为人工导入流程。
业界对比
金融终端厂商正把数据封装为 MCP/Skills 开放（Wind MCP、iFinD MCP）——接口化接入是行业方向。
设计巧思
数据源的'证据等级'应该像引用文献一样显式出现在报告里。

维度 3 · 并行取数：并发、限流与部分失败降级

深挖维度
价值点：多路并行的工程难点全在'失败时怎么办'——这是把分布式系统经验迁移到 agent 的主战场。
Struggle
早期并发拉满导致上游限流封禁；单源失败阻塞整体报告生成。
问题拆解
拆成并发度、限流、超时分级、失败语义四件事：哪些失败可重试、哪些要降级、哪些要标注缺口。
调研与测试
复用异步轮询框架的并发控制与超时分级经验；参考 bulkhead（舱壁）隔离模式。
解决步骤
  • 每源独立信号量限流
  • 超时分级：快源 5s / 慢源 15s
  • 失败重试（幂等）+ 熔断
  • 部分失败时报告显式标注'该维度数据缺口'而非编造
验证思路
混沌演练：人为掐断单源，验证报告降级路径与标注正确性。
达成效果
单源故障不再阻塞整体产出；数据缺口 100% 显式标注。
迭代新问题
部分失败时报告质量下降 → 化解：缺口维度显式声明 + 建议补充数据源。
业界对比
bulkhead 舱壁隔离与超时分级是微服务成熟实践——agent 的多路取数本质是分布式 IO 编排。
设计巧思
降级不是失败，是'诚实地告诉用户我知道多少'。

维度 4 · 证据治理：去重、口径对齐与打分

深挖维度
价值点：多源证据不治理就互相打架：同一指标三个口径，报告自相矛盾。
Struggle
不同源'营收'统计口径不同（含/不含某业务），报告前后数字打架被业务方打回。
问题拆解
治理三步：去重（同文多源）→ 口径对齐（时间窗/统计范围/单位）→ 打分（权威度×新鲜度×相关度）。
调研与测试
调研证据置信度评估方法；与业务方共建'口径映射表'（哪些指标口径可互换、哪些不可）。
解决步骤
  • 指纹去重（SimHash/标题+时间）
  • 口径映射表驱动的对齐
  • 证据分数 = 来源权重 × 新鲜度衰减 × 相关度
  • 分数低的证据只在'补充'区出现
验证思路
人工标注口径冲突样本集，验证对齐规则召回率。
达成效果
口径冲突导致的返工下降【占位：__%】。
迭代新问题
口径映射表维护成本 → 化解：冲突样本自动积累 + 季度评审更新映射表。
业界对比
金融研究终端（Wind 报告神笔等）把口径对齐作为核心卖点——印证这是投研场景的真痛点。
设计巧思
口径对齐的本质是'元数据质量'——数字的可比性由元数据决定。

维度 5 · 交叉校验：数字双源一致与 claim-evidence 绑定

深挖维度
价值点：数字是金融报告的红线：一个错误数字就能摧毁整份报告的可信度。
Struggle
报告偶发数字与源数据不符（模型在压缩/改写中抄错）。
问题拆解
把报告拆成原子 claim（每条带证据引用），分类校验：数字类双源一致、事实类有源可查、观点类标注'推断'。
调研与测试
调研 claim-level verification 与 LLM-as-judge 的校准方法。
解决步骤
  • 生成后自动拆 claim → 逐条对照证据核对
  • 数字不一致的 claim 打回重生成或删除
  • 观点句强制带'推断'标记
验证思路
claim 级抽检：人工核对自动校验的漏报/误报率。
达成效果
数字错误率降至【占位】；'推断'标记提升报告可信度。
迭代新问题
校验误报打断生成流程 → 化解：误报样本回流校验器，阈值随校准调整。
业界对比
学术上的 claim verification 与金融审计的'数字勾稽'思想一致——都要求每个数字可回溯。
设计巧思
claim-evidence 绑定让'幻觉'从感觉问题变成可审计的工程问题。

维度 6 · 长报告生成：分节、上下文预算与证据句柄化

深挖维度
价值点：多源证据总量远超上下文窗口：全量塞入既不可能也降低质量。
Struggle
20+ 证据文件远超窗口；早期直接截断导致报告后半部分无证据支撑。
问题拆解
按报告结构分节，每节独立生成：只携带该节相关证据子集；节间通过'大纲状态'保持一致性。
调研与测试
参考 Manus 的文件系统当上下文与分节生成实践；map-reduce 式证据摘要。
解决步骤
  • 证据句柄化：全文存文件/库，上下文只放句柄+摘要
  • 分节生成，节间传递'结论卡'而非全文
  • 最后一致性 pass：统一术语与数字
验证思路
节间一致性（同一数字全文一致）+ 大纲覆盖率评估。
达成效果
报告长度不再受窗口限制；节间矛盾率下降【占位】。
迭代新问题
节间风格漂移 → 化解：统一写作风格指令 + 末次润色 pass。
业界对比
长文档生成的分治（map-reduce）是学术界与工业界共识（LLMCompiler 的并行思想同源）。
设计巧思
证据句柄化 = 把窗口问题转化为检索问题。

维度 7 · 上下文超限的压缩与裁剪（证据远超窗口）

深挖维度
价值点：deep research 的证据量通常是窗口的 10~50 倍：压缩策略就是产品质量。
Struggle
多源证据累积到几十份后必然超窗，早期直接截断后半证据——报告后半段变成'没有证据的推断'。
问题拆解
压缩按'保留什么'分三档：数字与结论（必须原文保留）、论据（压缩为要点）、过程性文本（丢弃）；再加全局预算分配（每节 token 上限）。
调研与测试
对比 map-reduce 摘要 / 选 top-k / 层级压缩的质量成本曲线；参考 CE 综述的压缩分类。
解决步骤
  • 证据分数排序 → 预算内装箱（分数高先入）
  • 同源证据合并摘要
  • 跨节共享'全局事实卡'（关键数字只抽一次）
验证思路
压缩前后信息保留率（关键数字/结论抽取对照）+ 下游生成质量对比。
达成效果
在预算内保留【占位：__%】关键信息；报告质量无感损失。
迭代新问题
压缩丢掉冷门但关键的反例 → 化解：反例类证据加权保留。
业界对比
Manus 的文件系统句柄化与分层压缩是业界代表性路线。
设计巧思
压缩的判断标准只有一个：这句话被引用的概率。

维度 8 · 成本工程：模型分级与预算上限

深挖维度
价值点：deep research 单次任务 token 是对话的几十倍：不做分级就是烧钱。
Struggle
全流程用同一个旗舰模型跑一次任务，成本被业务方质疑；换成便宜模型后规划质量又明显下降。
问题拆解
按'认知密度'分级：规划与校验用强模型（错误代价高），检索式取数与摘要用便宜模型，格式整理用最小模型。
调研与测试
调研各家模型的单位成本与能力边界（强模型做错规划=全部返工；弱模型做错摘要=可容忍）。
解决步骤
  • 规划/校验 = 强模型；取数/摘要 = 轻模型；格式 = 最小模型
  • 全局 token 预算上限，超预算触发降级（减深度/减源）
  • 缓存复用（相同子问题与证据不重复处理）
验证思路
分级前后质量 A/B + 成本对比；预算触发率监控。
达成效果
单次任务成本下降【占位：__%】，质量回归无显著差异。
迭代新问题
便宜模型摘要丢关键信息 → 化解：摘要质量抽检 + 关键证据升级强模型。
业界对比
多家产品采用'强模型规划 + 轻模型执行'的混合编排——成本结构是产品设计的一部分。
设计巧思
成本工程的核心：把'贵的模型'花在错误代价最高的环节。

维度 9 · 评测：fact 层与 report 层双层评估

深挖维度
价值点：报告类产品的评估最难：既要有硬指标，也要评估'像不像一份好报告'。
Struggle
只有人工评估时，每次迭代无法客观归因；评审标准因人而异。
问题拆解
fact 层：报告拆成原子 claim 逐条对证据核验（可自动化）；report 层：结构/覆盖度/深度/可用性 rubric（人工+LLM 混合）。
调研与测试
调研 claim-level verification、rubric 评估与 LLM-as-judge 校准（人工金标对齐）。
解决步骤
  • fact 层自动化回归（每次迭代必跑）
  • report 层月度人工评估（评分卡）
  • 与人工分析师产出做盲评对比
验证思路
judge 与人工一致率校准；评估集与真实需求分布对齐。
达成效果
迭代有了客观尺子：每次改进可量化【占位：__】。
迭代新问题
评估集变大后回归变慢 → 化解：分层抽样回归 + 变更相关层全量跑。
业界对比
LLM-as-judge 的校准方法（人工金标对齐）是当前评测工程的主流实践。
设计巧思
双层评估让'质量'同时拥有硬指标与专业判断。

维度 10 · 迭代路线与数据埋点：从可用到 RL 化

深挖维度
价值点：deep research 的终局是 RL 训练（DeepResearcher 路线），而 RL 的前提是环境与奖励——即埋点与评测。
Struggle
编排式方案遇到天花板：检索策略靠人写规则，长尾场景永远覆盖不全。RL 化缺环境与奖励基建。
问题拆解
把演进拆三步：①编排式上线积累真实任务与结果 ②埋点与评测集升级为'可验证奖励'（事实核对自动打分）③小规模 RL/偏好优化实验。
调研与测试
DeepResearcher（真实 web 环境 GRPO）与 Search-R1 的奖励设计；Tongyi 的合成数据 + agentic RL 配方。
解决步骤
  • 全链路埋点：每次取数/校验/生成决策留痕
  • 用户采纳行为（直接用/编辑后用/弃用）作为弱奖励
  • 编辑 diff 作为偏好对数据来源
验证思路
奖励与人工判断的一致性校准；小规模实验对照编排基线。
达成效果
完成 RL 化的数据与奖励准备【占位：进展】。
迭代新问题
用户编辑行为含主观风格 → 化解：只取事实性修改作为奖励信号，风格修改过滤。
业界对比
Search-R1 → DeepResearcher → Tongyi DeepResearch 是 RL 化 deep research 的演进三部曲。
设计巧思
埋点不是运营工具，是未来 RL 的奖励基建——今天的数据决定明天能训什么。

异常处理 Case 集（高频拷打）

异常 case：搜索/数据源 API 限流（429）
每源独立令牌桶限流 + 指数退避重试；持续限流则切换备用源或标注缺口。经济性权衡：备用源可能是收费接口，只在主源连续失败时启用。
异常 case：规划出循环依赖（子问题 A 依赖 B，B 又依赖 A）
规划输出做 DAG 校验，发现环则合并或拆解重排；重排仍失败则人工介入模板。
异常 case：证据全被校验剔除（数据缺口）
绝不编造：报告显式输出'该维度数据缺口'并列出已尝试的检索路径——把失败转化为数据建设需求。
异常 case：并行部分失败导致报告不平衡
缺维度时报告自动降级为'已有维度 + 缺口说明'；用户体验上宁可短不可错。
异常 case：节间数字不一致
生成时传入'全局事实卡'（关键数字唯一来源），最后一致性 pass 再扫一遍数字与术语。
异常 case：工具循环调用
同工具同参数连续调用计数上限 + 全局步数预算（超限终止并输出已有结论）；循环检测信号回喂给规划器重规划。
