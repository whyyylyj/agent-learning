基金组合绩效评价（金融 DeepResearch）：10 个可以深挖的维度

怎么用：面试官追问"再深入一点"时，每个维度都是一条完整的防线，按六步方法论展开——① 问题定义（把症状翻译成可度量的工程问题）→ ② 问题分析（根因链 + 排除的假设与证据）→ ③ 问题场景（具体现场与复现方式）→ ④ 方案对比（三个候选的优劣与结论）→ ⑤ 采用与踩坑（第一版怎么翻车、怎么改）→ ⑥ 验证与迭代（指标、回归、后续演进）。红色"面试官深挖预演"是站在面试官视角的追问与亮点回答。黄色高亮为待填真实数据。

维度 1 · 场景识别与 skill 适配层：用户提问 → 技能路由

深挖维度
价值点：银行、保险、券商的用户提问形态各异，一个通用 agent 硬接所有问题，要么理解偏差要么漏分析步骤——skill 适配是绩效评价系统的第一道架构。
① 问题定义
灰度期的症状：同一句“这个组合最近表现怎么样”，银行理财经理要的是收益+回撤速览，券商投顾要的是归因到持仓的贡献分解——通用 agent 各给各的答案，都没有完整覆盖分析框架。定义为“场景-技能匹配率”问题：提问被路由到正确 skill 且分析框架完整执行的比例，初期抽测不足七成【占位：__%】。漏步骤比答错更隐蔽：数字都对，但归因没做、基准没比——结论表面成立实则残缺。
② 问题分析
关键洞察：绩效评价的问题空间是有限集。不像开放研究，基金组合分析的分析框架高度模式化——收益评价、风险评价、业绩归因、基准对比、持仓穿透、调仓评估等 N 类，每类有固定的组件编排套路。通用 agent 每次现场发挥等于每次重新发明分析流程，既不稳定也浪费。第二层分析：skill 粒度是关键变量——粒度太细（拆 20 个）路由错误率高且编排碎片化；太粗（一个大 skill）等于回到通用 agent。
③ 问题场景
现场：“为什么这个组合二季度跑输基准 2 个点？”——正确路径是基准对比→收益分解→归因下钻→结论四步，涉及 3 个 skill 的编排。早期通用 agent 只做了收益对比就下结论“跑输因为跌幅大”——归因环节整个缺失，投顾拿到的是正确但无用的答案。复现：50 道框架完整性探针题，统计漏步骤率。
④ 方案对比
方案优势劣势/风险结论
单一通用 agent 端到端零路由成本，长尾灵活分析框架不保证完整；不可复现；token 成本高否
意图分类直连固定 workflow确定性强、可复现刚性：问题稍有变化就接不住；新场景要改代码否
skill 库 + 编排：场景识别 → skill 选择 → Plan/ReAct 编排框架完整性由 skill 保证；描述式路由零训练成本；skill 可独立迭代路由层要维护 skill 卡片；编排层复杂度上升采用
⑤ 采用与踩坑
采用三层：场景识别（结合机构类型、提问语境、组合上下文）→ skill 适配（skill 卡片含场景描述 / 输入输出契约 / 前置条件 / 组件编排模板）→ Plan/ReAct 执行。踩坑一：初版 skill 拆成 20 个，路由错误率飙升——按分析框架聚合到 8 个，每个 skill 内部再参数化，路由错误率腰斩【占位：__%】。踩坑二：skill 描述文档就是路由的 prompt 上下文，描述模糊路由就漂——skill 卡片结构化重写（固定字段：适用场景 / 不适用场景 / 典型问法 / 输出物），路由稳定性显著提升。踩坑三：不该接的问题（“帮我预测明天涨跌”）被硬接——加入 irrelevance 检测（BFCL V3 同款思路），明确拒答并说明系统边界。
⑥ 验证与迭代
场景-skill 匹配率标注集（每 skill 100+ 条）离线评测；框架完整性探针（每类 skill 的必做步骤清单）线上抽检；匹配率提升至【占位：__%】。迭代：新 skill 上线走“LLM 兜底先行 → 样本积累 → 固化为 skill 卡片”的路径，与案例一意图分层的进化流水线同构。
业界对比
东方财富妙想的 Skills 能力体系、Dify/Coze 的技能化编排是同一趋势——分析型 agent 正从“万能对话”转向“技能编排”。
设计巧思
领域 agent 的护城不是通用智力，是把分析方法论固化为 skill 的领域工程。

🔥 面试官深挖预演

追问 1
Q：为什么不微调一个场景分类模型？
A：skill 集合会增删——描述式路由（skill 卡片即上下文）零训练成本随改随生效；微调模型每次 skill 变更都要重训。等路由样本积累够多，把高频场景下沉为便宜层是顺理成章的优化，架构上预留了这条路。
追问 2
Q：skill 和 function calling 有什么区别？
A：function 是单次工具调用，skill 是分析框架——一个 skill 内部编排了多个组件的调用顺序、中间结果传递和校验规则。skill 是“食谱”，工具是“食材”，这层抽象让 agent 从“会用工具”升级到“懂分析方法论”。

维度 2 · 数据层复用：不建新数据源，复用已有资产

深挖维度
价值点：绩效评价系统底下的数据层（基金净值、持仓、组合、基准、因子）原系统早就有了——agent 层的任务是复用而不是重建。
① 问题定义
架构评审时的核心决策：agent 要访问的数据（净值序列、持仓明细、组合构成、基准曲线、因子暴露）在原系统数据层全部存在且经过多年校验。问题定义：复用与重建的边界在哪里？量化背景：两套数据层的口径分裂是致命风险——用户拿 agent 结论与原系统页面对照，出现“系统里 7.2%、agent 说 7.1%”就是信任崩塌事故，而重建数据管道产生口径漂移的概率接近必然。
② 问题分析
逐项分析数据需求：agent 需要的数据按“读取模式”分三类——批量时序拉取（净值、收益率序列）、明细查询（持仓、交易）、聚合计算（区间收益、风险指标）。前两类原数据服务 API 直接覆盖；第三类属于计算不属于数据——是能力组件的事（见维度 3）。真正的缺口只有一个：原 API 为页面交互设计，单次粒度小，agent 一次评价要串几十次调用——这是接入层要解决的工程问题，不是重建数据层的理由。
③ 问题场景
现场：绩效评价要算某组合近三年逐月收益+回撤+相对基准偏离，按原页面 API 逐月拉取要 36 次调用，单次任务耗时分钟级且容易被限流。而数据层其实有批量端点的可能性——这是接入模式问题不是数据缺失问题。
④ 方案对比
方案优势劣势/风险结论
agent 直连数仓写 SQL灵活权限绕过应用层、口径无治理、SQL 不可审计——三关全挂（NL2SQL 同款死因）否
复用已有数据服务 API + 协商补批量端点口径与源系统天然一致；权限模型继承；审计可行要说服数据团队为 agent 场景改造；页面粒度 API 需要适配层采用
为 agent 新建专用数据视图层读写隔离，定制自由两套口径的漂移风险永久化；双倍维护成本否
⑤ 采用与踩坑
采用：复用原数据服务 API 为唯一数据入口，权限透传（机构 / 用户 / 组合范围的可见性原样继承）；与数据团队协商新增批量时序端点（一次拉区间序列）。踩坑一：agent 流量与生产页面流量共享数据层配额——早高峰评价任务与理财经理打开页面抢配额，页面卡顿被投诉——为 agent 通道独立配额 + 错峰执行批量任务。踩坑二：部分老接口无字段级口径说明（“收益”是费前费后不明确）——拉通数据团队补口径字典，接口元数据带口径标签。踩坑三：接口超时按页面标准（30s）设置，agent 多步编排里一步挂全链挂——接入层统一收敛超时并分级。
⑥ 验证与迭代
数字一致性基线：agent 链路产出的核心指标与原系统页面抽样对账，一致率必须 100%（口径标签对齐后）；数据层零事故【占位：__】。迭代：批量端点按 agent 使用频率逐步扩容，形成“高频访问模式 → 沉淀为专用端点”的数据服务演进循环。
业界对比
Wind MCP、iFinD MCP 的行业方向就是“数据能力接口化开放”——数据层复用 + 接口化封装与整个行业趋势同构。
设计巧思
agent 项目的第一架构决策往往不是“用什么模型”，是“复用什么、新建什么”——口径一致性比任何智能都值钱。

🔥 面试官深挖预演

追问 1
Q：复用老系统 API 会不会被老系统的性能拖累？
A：会，所以做了三件事：批量端点消解调用次数、独立配额避免与生产抢资源、超时分级让 agent 步骤快速失败。复用的收益是口径一致性和权限继承——这两个用钱买不到，性能问题反而有标准解法。
追问 2
Q：为什么坚决不让 agent 写 SQL 查数仓？
A：权限（生成的 SQL 绕过应用层权限模型）、口径（统计口径无法受控）、审计（没人能审一段生成的 SQL）三关都过不了。金融场景里这三个都不是技术偏好是监管要求。

维度 3 · 能力组件的 agent 化封装：内部组件 → 工具 API

深挖维度
价值点：原系统后面早就沉淀了绩效计算、风险指标、归因分析等能力组件——把它们封装成 agent 可调用的工具，是整个系统的核心工程。
① 问题定义
现状盘点：收益计算、波动率/回撤/夏普等风险指标、Brinson 归因、风格分析——这些组件以内部 RPC 形式存在，与页面逻辑耦合（入参依赖页面会话上下文、返回直接给前端渲染）。问题定义：如何把“给人用的组件”改造成“给 agent 用的工具”？判断标准三条：参数可从自然语言推导（schema 化）、调用可重试（幂等）、错误可理解（语义化）。
② 问题分析
逐条对照三条标准找差距：入参方面，组件要的会话上下文（产品线、当前组合 ID）agent 拿得到但要显式传，隐藏依赖必须显式化；幂等方面，查询类组件天然幂等，但要防止 agent 重试时重复计算浪费配额；错误方面，组件错误是内部错误码（“ERR-2043”），agent 无法据此决策重试还是换路——错误必须翻译成行为语义（可重试 / 需换参 / 需人工）。还有一个容易被忽视的维度：工具描述质量直接决定 ReAct 的工具选择准确率——描述是给模型看的 API 文档。
③ 问题场景
现场：agent 要算“组合二季度的 Brinson 归因”，工具选择正确但入参传了组合代码而非内部持仓快照 ID——组件静默返回了错误口径的结果（用最新持仓回溯历史归因）。这类“参数对了但语义错了”的失败最隐蔽：数字看起来完全合理。对策：工具入参做语义校验（时间点敏感参数必须显式传快照语义）。
④ 方案对比
方案优势劣势/风险结论
直接暴露内部 RPC零改造成本会话耦合、错误码不可理解、无 schema——agent 调用错误率高且不可归因否
建 agent 工具网关统一封装schema 标准化、错误语义化、鉴权限流统一、工具目录集中管理网关是新增组件要维护；封装层要跟组件版本对齐采用
按 agent 场景重写组件最贴合重复造轮子，丢掉原系统多年校验的正确性积累否
⑤ 采用与踩坑
采用 agent 工具网关：每个组件封装为工具卡片（名称 / 功能描述 / 入参 schema 含语义约束 / 出参结构 / 错误语义 / 典型调用示例）。踩坑一：工具描述最初由后端随手写，ReAct 工具选择错误率高——描述重写为“给模型看的文档”：典型问法、参数语义、边界条件，选择准确率大幅回升【占位：__%】。踩坑二：枚举型入参（组合 ID、基准 ID）模型经常幻觉编造——枚举值从数据层动态拉取注入候选列表，模型只能选不能编。踩坑三：工具数量增长后选择准确率衰减（工具越多干扰越大）——按 skill 分组限定可见工具集，每个 skill 只看得到自己的工具，选择空间收窄。
⑥ 验证与迭代
工具调用成功率（选择正确 × 参数合法 × 结果可用）分 skill 统计；参数幻觉率专项（枚举字段编造率必须为零——靠动态候选机制结构性保证）；错误分类统计驱动组件改造优先级。效果：工具调用一次成功率【占位：__%】，枚举幻觉结构性归零。
业界对比
MCP 的工具描述规范、各家 function calling 最佳实践都强调 schema 语义质量——工具工程正成为独立学科。
设计巧思
工具封装的本质是翻译：把“给系统的接口”翻译成“给模型的接口”——schema 是语法，描述与错误语义是语用。

🔥 面试官深挖预演

追问 1
Q：工具描述不就是个文档吗，值得当设计重点？
A：对 agent 来说描述就是 API 的全部——模型没看过你的代码，它对工具的全部认知来自描述。我们重写描述后工具选择准确率的提升，比换一个更强的模型还大。这是“提示工程在工具层的延伸”，很多人在这里失分。
追问 2
Q：怎么防止模型编造参数？
A：结构性防御：枚举类参数不给自由文本空间——候选值动态拉取、模型只能选不能编。参数幻觉靠 prompt 约束是压不干净的，靠机制才能归零。

维度 4 · Plan + ReAct 混合推理：任务 DAG 骨架 + 节点内 ReAct

深挖维度
价值点：纯 ReAct 一步步走会漂移，纯 Plan 一次规划定死无法应对执行反馈——绩效评价这种多步任务需要两者杂交。
① 问题定义
两类失败模式实测：纯 ReAct 模式下，长任务（十几步组件调用）出现方向漂移与循环——某次归因异常后 agent 反复重算同一指标五步不出结果；纯 Plan 模式下，规划一次定死，执行中发现数据缺失（某月持仓快照不全）无法补位，整单失败。定义为“长程任务的稳定性”问题：完成率、步数效率（实际步数/必要步数）、循环发生率三个指标刻画。
② 问题分析
根因分析：ReAct 的本质缺陷是局部性——每步决策只看上一步观察，缺乏全局任务视图，长链路误差累积必然漂移；Plan 的本质缺陷是刚性——规划时依赖的信息在执行中会失效（数据缺失、指标异常），无反馈通道。两者恰好互补：Plan 提供全局骨架（防漂移），ReAct 提供局部灵活（应对意外）。关键设计点：重规划的触发条件与预算——无限重规划等于失控，零重规划等于刚性。
③ 问题场景
现场：“对比组合 A 和 B 上半年的风险收益特征”——规划出 12 节点 DAG（各自指标计算 + 对比 + 结论），执行到 B 的波动率节点时数据缺失。纯 Plan 直接失败；纯 ReAct 早就漂了；混合模式：该节点触发受限重规划，跳过缺失项并标注“该指标数据缺口”，其余节点继续，最终交付带缺口声明的结论。
④ 方案对比
方案优势劣势/风险结论
纯 ReAct（思考-行动-观察循环）灵活、实现简单长任务漂移与循环；步数预算失控；不可复现否（保留在节点内部）
纯 Plan-and-Execute全局视图清晰、可复现刚性：执行期无反馈修正，数据缺失即全盘失败否
Plan 骨架 + 节点内 ReAct + 受限重规划骨架防漂移、节点内灵活、重规划带预算编排器复杂度高；状态传递设计要小心采用
⑤ 采用与踩坑
采用：先 Plan 生成任务 DAG（节点=组件调用或子分析，边=数据依赖），节点内 ReAct 处理参数准备与异常，节点间传递结构化中间结果。受限重规划：最多 2 次，且需满足触发条件（关键节点失败 / 覆盖率不足），重规划只调整受影响子图。踩坑一：中间结果全塞上下文，几步之后窗口爆炸且注意力稀释——状态外置为“任务黑板”（见维度 7），上下文只放当前节点所需。踩坑二：循环调用（同工具同参数反复调）——状态机防环：连续同参调用计数超 2 次强制跳出转重规划评估。踩坑三：重规划的触发阈值定太敏感，小异常也触发全局重规划，成本翻倍——区分“节点级失败”（局部处理）与“任务级失败”（才触发重规划）。
⑥ 验证与迭代
完成率、步数效率、循环发生率三指标进看板；完成率从纯 ReAct 的【占位：__%】提升至【占位：__%】，循环调用基本消除；同一问题多次执行的结果稳定性（可复现性）显著改善。迭代：重规划案例库积累——每次重规划的触发原因与处理方式落盘，反哺规划器的 few-shot 示例。
业界对比
Plan-and-Execute 与 LMCompiler（并行函数调用）是学术参照；Anthropic 编排者-执行者实践互相印证。
设计巧思
骨架防漂移，肌肉防僵硬——长程任务的稳定性来自两种推理模式的杂交，而不是二选一。

追问 1
Q：为什么不干脆端到端 RL 训一个策略？
A：DeepResearcher 证明端到端 RL 可行且效果更好，但它需要环境与奖励基建。工程节奏：编排先拿业务结果、沉淀任务轨迹与评价，这些轨迹就是未来 RL 的训练数据、评测就是奖励函数——两步走不冲突，是先后手。
追问 2
Q：Plan 和 ReAct 的边界怎么划？
A：按“不确定性在哪”划：分析框架（做什么、什么顺序）是确定性的，Plan 管；执行细节（参数怎么凑、异常怎么处理）是不确定的，ReAct 管。确定性上收、不确定性下放——和案例一意图路由“确定性走便宜层”是同一个设计哲学。

维度 5 · 并行计算编排：多指标并行调用组件 API

深挖维度
价值点：一次绩效评价要调 20+ 次组件（多指标 × 多组合 × 多区间），串行分钟级用户等不了，并发拉满会把共享数据层打挂——并行编排是工程主战场。
① 问题定义
量化问题：串行执行单次评价 3~5 分钟【占位：__】，用户预期 30 秒内给分析；而天真地把并发开满（全组件同时打），数据层 QPS 冲击引发限流，连累同租户的生产页面。定义双约束：时延目标（30s 内完成计算编排）+ 礼貌约束（agent 流量不得影响生产流量）——后者是复用内部数据层的特殊代价。
② 问题分析
并行化的结构分析：组件调用间存在依赖图——收益指标之间独立（可并行），归因依赖收益结果（必须后置），对比依赖双方各自完成（汇合点）。并行度上限由两件事决定：无依赖节点的宽度（约 8~12【占位：__】）和数据层每端点的配额。真正要设计的是“依赖感知调度 + 全局并发闸门 + 失败语义”三件套，其中失败语义最容易被忽视：部分组件失败时，整单失败？降级交付？等待重试？——不同指标的重要性不同，答案不该一刀切。
③ 问题场景
现场：早盘集中来了 5 个评价任务，每个 30+ 组件调用，并发全开——数据层某核心端点 QPS 超限，触发限流，连理财经理的页面查询都开始超时。这次事故确立了“agent 流量必须让路生产流量”的铁律。
④ 方案对比
方案优势劣势/风险结论
全串行对上游零压力，实现简单分钟级时延，用户体验不可接受否
全并行 + 全局线程池时延最优打挂数据层、连累生产页面；失败语义混乱否
依赖感知 DAG 并行 + 每端点独立限流 + 分级降级时延与上游友好的平衡点；失败有语义调度器复杂；配额要持续调优采用
⑤ 采用与踩坑
采用：调度器按 DAG 拓扑就绪即调度（无依赖节点并行执行），每端点独立令牌桶限流（配额与数据团队书面约定），核心指标失败重试（幂等）+ 熔断，非核心指标失败标注缺口继续。踩坑一：超时一刀切导致快端点被拖、慢端点被掐——超时分级（快端点 5s / 重计算端点 15s），并按 P90 实测持续校准。踩坑二：重试风暴——某端点抖动时多任务同时重试放大压力——指数退避 + 熔断半开探测。踩坑三：部分失败时报告“静默缺项”（用户不知道少了指标）——缺口显式化：报告里明确标注“该指标因数据缺口未计算”，把降级变成透明的信息而不是隐藏的缺陷。
⑥ 验证与迭代
P50/P99 编排时延进看板；单次评价从【占位：__】分钟降到【占位：__】秒；数据层因 agent 流量的限流事件归零（配额看板双向可见）；缺口标注率 100%（凡是缺项必声明）。混沌演练：定期人为掐断单端点验证降级路径。
业界对比
bulkhead 舱壁隔离与超时分级是微服务成熟实践——agent 的多路调用本质是分布式 IO 编排，功底直接迁移。
设计巧思
降级不是失败，是“诚实地告诉用户我知道多少”——缺口显式化比静默残缺专业一个量级。

追问 1
Q：并发度怎么定的？
A：三层决定：DAG 无依赖宽度决定理论上限、每端点配额决定实际上限、成本预算决定意愿上限——三者取最小。而且配额不是抢来的是和数据团队协商的，agent 流量让路生产流量是复用内部数据层的铁律，这背后的判断是：系统整体的可用性高于单次任务的时延。
追问 2
Q：这和一般的微服务调用编排有什么区别？
A：骨架是同一套（依赖感知调度、舱壁隔离、熔断降级——分布式基本功的直接迁移，我的异步轮询框架经验全用上了），新问题在失败语义的“业务化”：传统编排失败就是失败，agent 编排要区分“这个指标缺了报告还成不成立”——失败语义成了业务判断，这是 agent 工程给分布式编排带来的新维度。

维度 6 · 结果勾稽与数字校验：agent 结论必须与原系统对得上账

深挖维度
价值点：用户会拿 agent 的结论与原系统页面互查——任何一处不一致都是信任事故。绩效评价的数字红线：勾稽一致。
① 问题定义
定义“勾稽一致”：agent 输出的每一个数字，与其数据来源（组件返回 / 数据层取值）逐位一致，且口径（费前费后、日历年 vs 交易日、万元 vs 亿元）显式声明。灰度期抽测发现三类不一致：转写错误（模型抄错——“120.3 亿”写成“102.3 亿”）、口径漂移（agent 用费前收益对比费后基准）、精度不一致（四舍五入规则不同导致尾差）。任何一类都足以让用户否定整个系统。
② 问题分析
三类根因分开治：转写错误的本质是“数字经过了生成环节”——模型在压缩、改写、组织语言时对数字做的是概率性复制；口径漂移的本质是元数据缺失——数字离开组件时没带走自己的口径标签；精度不一致是工程细节——舍入规则没有全局约定。第一类是结构性风险：只要数字过 LLM 笔头就有抄错概率，治本方案是数字不过 LLM（与案例一佣金链路同款原则的复用）。
③ 问题场景
现场：投顾把 agent 生成的评价报告里的“组合年化收益 7.21%”截图给客户，客户自己打开系统看到 7.2%——尾差（agent 舍入到两位、系统一位）。客户问“到底哪个对”，信任瞬间归零。从此确立：舍入规则全局统一，且报告数字必须与页面显示规则一致。
④ 方案对比
方案优势劣势/风险结论
生成后人工逐数核对可靠一次报告几十个数字，人力不可持续否
claim 级勾稽：报告拆原子命题逐条对账 + 口径标签强制自动化可持续；错误可定位到环节要建 claim 拆解与数字回链的基建采用
全模板拼装（数字不进生成）结构性根除转写错误分析结论的组织与表述灵活性大幅下降部分采用（数字段模板化，叙述段生成）
⑤ 采用与踩坑
采用混合：报告拆成原子 claim，数字类 claim 强制走模板段（数字原样透传不过 LLM 改写），叙述类 claim 生成后逐条勾稽对账。组件返回强制带口径元数据（费前/费后、时间窗类型、单位、舍入规则），报告展示口径标签。踩坑一：claim 拆解粒度定不好——太粗对不上账、太细成本高——按“一个数字一个 claim”的最小原则落地。踩坑二：勾稽误报打断生成流程——误报样本回流校验器迭代阈值，区分“真不一致（打回）”与“格式差异（放过）”。踩坑三：口径标签一开始只有单位——补全时间窗语义（“近一年”是自然年还是滚动 365 天必须显式）。
⑥ 验证与迭代
数字勾稽一致率（agent 报告数字 vs 组件返回原文）纳入每次回归，目标 100%；口径标签覆盖率 100%；转写错误率结构性归零（数字段不过 LLM）；用户报告的数字质疑工单清零【占位：__】。
业界对比
金融审计的“数字勾稽”思想与学术 claim verification 同构——每个数字可回溯是共同底线。
设计巧思
勾稽一致是 agent 结论进入金融决策链的准入证——宁可少说，不可说错。

🔥 面试官深挖预演

追问 1
Q：为什么数字经过 LLM 就一定会错？
A：不是一定，是概率——而金融场景对数字的错误容忍是零。生成模型对数字做的是概率性复制，链路越长抄错概率越高。结构性解法就是不让它抄：数字段模板化透传，叙述段再灵活。这与我在保险佣金链路用的是同一条原则——数字不过 LLM，跨场景复用的架构原则本身就是亮点。
追问 2
Q：口径问题怎么彻底防住？
A：元数据前移：数字在组件返回时就带全口径标签（费前费后/时间窗/单位/舍入），报告只是透传标签。口径不是生成时“注意”的事，是数据结构里自带的事。

维度 7 · 多步推理的中间结果治理：任务黑板与状态外置

深挖维度
价值点：十几步组件调用产生的中间结果（指标表、持仓快照、归因中间量）全塞上下文，几步就撑爆窗口且注意力稀释——状态外置是必选项。
① 问题定义
症状：任务进行到 8~10 步，上下文里堆着前面所有组件的完整返回（每段几百到几千 token），出现两类问题：窗口超限直接报错；更隐蔽的——没超限但模型开始“看不见”早期的关键数字（长上下文注意力稀释），后续计算引用错对象。定义为“中间结果的生命周期管理”问题：每个中间结果应该在什么阶段以什么形态存在于哪里。
② 问题分析
分析中间结果的访问模式：绝大多数中间结果只在“产生它的节点”和“消费它的节点”被需要（局部性），只有少数（关键结论、全局约束、口径标签）需要全程可见（全局性）。这个访问模式直接给出解法：局部结果外置存储（按句柄引用），全局信息进小型黑板。类比操作系统：内存放活跃数据，磁盘放全量数据，页表做映射——黑板就是页表。
③ 问题场景
现场：归因分析节点需要“区间收益”节点的结果，但那个结果在 6 步之前、上下文 1.2 万 token 之前——模型引用了另一个组合的收益数字（两个组合的中间结果长得几乎一样）。这类“张冠李戴”错误在中间结果堆积后频发，且肉眼难察。
④ 方案对比
方案优势劣势/风险结论
全量中间结果进上下文模型看得最全窗口爆炸；注意力稀释引发张冠李戴否
全量外置 + 需要时检索回填窗口友好检索回填有延迟与错取风险；数字类结果检索错代价高否（作为补充）
分级：数字类句柄化 + 结论进黑板 + 过程性结果外置关键信息常驻、按需取用、窗口可控分级逻辑与读写协议要精心设计采用
⑤ 采用与踩坑
采用任务黑板：全局区（任务目标、全局约束、口径标签、关键结论卡——常驻小体积）+ 局部区（各节点中间结果，句柄化存储按需拉取）。数字类中间结果永不摘要、只句柄化（数字一经摘要就有失真风险）。踩坑一：黑板写入协议不清，多个并行节点并发写冲突——黑板分区加版本号，写入走追加不改写（append-only），冲突以最新版本为准并留痕。踩坑二：句柄拉回时的“取错”问题——句柄带语义描述（节点名 + 数据内容摘要），拉取前先验描述匹配。踩坑三：黑板本身越写越大（结论卡累积）——结论卡也分级：当前节段的结论常驻，历史节段结论合并为高层摘要（但数字仍然原文保留在句柄层）。
⑥ 验证与迭代
长任务（15+ 步）完成率提升【占位：__%】；中间结果引用错误（张冠李戴）在探针集中归零；单任务上下文峰值下降约六成【占位：__%】。迭代：黑板的“哪些信息该常驻”规则随 badcase 持续调优——本质是在为这个领域学习“注意力该往哪放”。
业界对比
Manus 的文件系统当上下文（句柄化）与 LangGraph checkpoint（状态外置）是业界两条代表路线，黑板是两者与领域规则的杂交。
设计巧思
上下文管理的本质不是塞多少，是让模型在每一步看见“该看的”——黑板是给注意力做的操作系统。

🔥 面试官深挖预演

追问 1
Q：这和 LangGraph 的 checkpoint 有什么关系？
A：同族思想不同层次：checkpoint 解决“断点恢复”（持久化），黑板解决“注意力分配”（什么该被模型看见）。我们的黑板在 checkpoint 之上加了领域分级——数字句柄化、结论卡常驻——这是通用框架没给的，要对业务错误做归因后才设计得出来。
追问 2
Q：数字为什么不摘要？
A：数字摘要=概率性改写，3.14159 摘成“约 3.14”在叙述里没问题，在勾稽链里就是错。我们对中间结果的态度和报告层一致：数字只有原文形态，要么全文要么句柄，没有第三种。

维度 8 · 上下文超限的压缩与裁剪：证据与历史的分层预算

深挖维度
价值点：多组件返回累积远超窗口：压缩策略直接决定成本与质量——这一维与案例一的压缩一脉相承但对象不同（指标表 vs 对话历史）。
① 问题定义
对象变了：案例一压缩的是“对话历史 + 检索证据”，这里压缩的是“组件返回的指标表 + 中间结论 + 任务指令”。量化：一次完整评价的原始中间结果总量 3~8 万 token【占位：__】，可用窗口预算 1.2 万——压缩比要求 3~6 倍，且数字不能失真、口径不能丢、约束不能摘掉。
② 问题分析
按“可压缩性”给内容分类：过程性文本（推理轨迹、冗余字段、调试信息）可丢弃；叙述性结论可摘要；数字与口径标签不可压缩只能句柄化；任务约束与全局状态常驻。压缩的判断标准只有一条：这句话后续被引用的概率——高概率常驻，低概率外置，零概率丢弃。误判代价不对称：把“会被引用的”丢了（报告出错），比把“不被引用的”留着（多花 token）严重得多——所以关键类宁可高估。
③ 问题场景
现场：早期统一摘要压缩，一次评价后报告里“最大回撤”与正文叙述对不上——摘要时把回撤的“区间口径”摘掉了（回撤值不带区间就没有意义）。从此确立：口径标签与数字绑定为原子单位，不可分割、不可摘要。
④ 方案对比
方案优势劣势/风险结论
统一摘要压缩全部历史实现简单数字失真、口径丢失——金融场景致命否
top-k 截断（留分数最高的）简单可控分数不等于后续需要；关键约束可能被截否
分类压缩 + 预算装箱：不可压类句柄化、可摘类摘要、按节点预算分配失真风险结构性消除；预算可控分类规则与预算分配需要持续调优采用
⑤ 采用与踩坑
采用：内容四分类（不可压 / 可摘 / 可弃 / 常驻）+ 分节预算（每节 token 上限，全局约束与数字句柄优先装箱）。踩坑一：预算平均分配导致关键分析节 starving——预算按节点重要性加权（结论节 > 分析节 > 过程节）。踩坑二：摘要丢“冷门但关键”的反例信息（某指标的异常值）——反例类内容加权保留（异常值是分析的金子不是噪音）。踩坑三：压缩后的上下文模型“找不到”句柄内容——句柄进上下文时带语义描述与典型值，模型能判断“要不要拉取”。与维度 7 的黑板共用一套句柄体系。
⑥ 验证与迭代
压缩前后关键信息保留率（数字与口径全量保留是硬约束，叙述类人工评估）；下游报告质量 A/B（压缩策略 vs 全量基线在短任务上对比）无显著差异；单任务 token 成本下降约五成【占位：__%】。
业界对比
CE 综述的压缩分类（压缩什么/何时/如何）与 Manus 的分层路线是理论坐标；我们的贡献是把“不可压类”精确到金融语义（数字+口径原子绑定）。
设计巧思
压缩的判断标准只有一个：这句话被引用的概率——而金融语义决定了“数字+口径”的被引用概率永远是 100%。

🔥 面试官深挖预演

追问 1
Q：为什么不用长上下文模型一劳永逸？
A：窗口大不等于注意力好——长上下文的中间信息利用率实证下降（lost-in-the-middle），而绩效评价恰恰是“中间的数字最重要”。且成本随窗口线性涨，分级压缩是结构解。
追问 2
Q：压缩规则怎么来的？
A：从错误反推：每一次“引用错对象”或“口径丢失”的 badcase 都归因到分类规则，修正规则再回归。压缩策略不是设计出来的一次性产物，是被 badcase 喂出来的运营资产。

维度 9 · 成本工程：模型分级与 token 预算

深挖维度
价值点：DeepResearch 形态的单次任务 token 消耗是对话的几十倍——不做分级就是烧钱；而绩效评价的环节错误代价高度不对称，分级有明确的依据。
① 问题定义
量化背景：全流程用旗舰模型，单次评价成本是普通问答的约 40 倍【占位：__】；直接全线换成便宜模型，规划质量崩塌（拆解错分析框架，全盘返工）。问题的正确形态不是“用哪个模型”而是“哪个环节用哪个模型”——分级的依据是错误代价：规划错 = 全部返工（最高代价），参数抽取错 = 单步重试（低代价），格式整理错 = 无伤大雅。
② 问题分析
按认知密度给环节分层：规划与勾稽校验是“高认知密度”环节（错误代价高、需要领域推理）——强模型；参数准备、结果格式化是“低认知密度”环节——轻模型；中间还有一档“中认知”（归因解读、结论组织）——中档模型。这个分层必须显式建模成配置而不是写死——因为“什么算高认知”随模型价格和能力变化。
③ 问题场景
现场：参数抽取环节（把“近三年”转成时间窗参数）用旗舰模型，单步 800 token、延迟 2s；换轻模型后单步 120 token、延迟 300ms，准确率几乎无损（这是模式化转换任务）。反过来试过把规划也换成轻模型——分析框架拆解错误率明显上升，一次拆错的返工成本抵消了十次省钱。
④ 方案对比
方案优势劣势/风险结论
全线旗舰模型质量上限最高成本不可持续；低价值环节烧高价值模型否
全线轻模型成本最优规划与校验环节质量崩塌，返工抵消节省否
按认知密度三级分级 + 全局预算成本与质量的帕累托前沿；错误代价对齐路由配置要维护；级别边界要校准采用
⑤ 采用与踩坑
采用三级：规划 / 勾稽校验 = 强模型；参数抽取 / 格式整理 = 轻模型；归因解读 / 结论组织 = 中档模型。全局 token 预算上限，超预算触发降级策略（减分析深度 / 减对比维度，缺口显式声明）。踩坑一：轻模型做参数抽取时枚举幻觉（编造组合 ID）——枚举动态候选机制结构性防御（见维度 3），与模型分级正交。踩坑二：轻模型摘要丢数字——数字类内容强制走强模型或不摘要（数字不可压缩原则再次生效）。踩坑三：分级配置写死在代码里，模型价格变动后失效——分级路由做成配置（环节→模型档位），价格与能力变化只改配置。与计费系统联动：模型分级直接改变 API 倍数成本结构，降本成果传导到客户账单。
⑥ 验证与迭代
分级前后质量 A/B（分析框架完整性、勾稽一致率无显著差异）+ 成本对比：单次任务成本下降约六成【占位：__%】；预算触发率监控（超预算降级的占比，过高说明定价或预算失衡）。迭代：环节-模型映射按“错误代价 × 单价”每季度重评。
业界对比
多家产品采用“强模型规划 + 轻模型执行”的混合编排——成本结构是产品设计的一部分（Anthropic：token 用量解释 80% 成本方差）。
设计巧思
成本工程的核心：把“贵的模型”花在错误代价最高的环节——分级依据是代价不对称，不是模型排行榜。

🔥 面试官深挖预演

追问 1
Q：分级的依据是什么，不会拍脑袋吗？
A：错误代价不对称性：规划错的代价是全盘返工，抽取错的代价是单步重试——代价差一到两个数量级，模型单价差不到一个数量级，所以贵模型花在高代价环节是严格占优的。而且这个映射是配置，随价格与能力重评，不是一次性决策。
追问 2
Q：和计费系统什么关系？
A：直接关系：模型分级改变单次任务的真实成本结构，计费的 API 倍数要反映这个结构——内部降本和对外定价是同一套成本观测的两个视图。成本工程做不好，计费倍数就是拍脑袋。

维度 10 · 评测体系与 RL 化演进：从编排到学习的路线图

深挖维度
价值点：编排式方案的天花板清晰可见：检索与调用策略靠人写规则，长尾场景覆盖不全。终局是 RL 训练（DeepResearcher 路线），而 RL 的前提是环境与奖励——也就是埋点与评测。
① 问题定义
现状的边界：skill 编排覆盖了高频分析框架（八成流量【占位：__%】），但长尾提问（表述多变、框架组合新颖）的处理质量 plateau——规则写不过来，写了的规则又互相打架。问题定义：如何从“编排的 plateau”走向“学习的扩展性”？分三步：编排积累数据 → 埋点评测升级为可验证奖励 → 小规模 RL 实验。
② 问题分析
RL 化的前置条件清单（对照 DeepResearcher / Search-R1 的配方）：环境（可交互的工具环境——我们已有：组件 API 网关就是环境）、动作空间（工具调用——已有）、奖励（事实正确性自动判定——缺！这正是要建的）。奖励设计的洞察：绩效评价的奖励比开放研究好做——数字勾稽一致率就是天然的 verifier 奖励（可自动计算、无歧义），分析完整性有 rubric——这是领域给 RL 的礼物。
③ 问题场景
现场：用户对报告做了三处编辑——改了一个结论的措辞、修正了一个时间窗表述、删了一段重复分析。前两类是有信号的事实性修改（奖励正样本），第三类是风格修改（噪声）。原始采纳行为直接当奖励会引入大量噪声——需要过滤。
④ 方案对比
方案优势劣势/风险结论
继续堆编排规则零新基建边际收益递减，长尾永远盖不住否（作为基线保留）
直接上 SFT 微调（拿好任务做监督数据）起步快只学形不学策：模仿轨迹不等于优化目标；坏轨迹混入难过滤暂缓
三步走：编排积累 → 可验证奖励 → 小规模 RL（GRPO 系）扩展性的正解；奖励可自动计算基建投入大；奖励噪声要治理采用（分阶段）
⑤ 采用与踩坑
已落地第一步、在建第二步：①全链路埋点——每次工具调用、参数、结果、勾稽输出、用户采纳行为（直接用 / 编辑后用 / 弃用）留痕；②奖励通道——数字勾稽一致率（verifier 奖励，自动）+ 分析完整性 rubric（模型评审，人工金标校准）。踩坑一：用户编辑行为混入风格修改噪声——只取事实性修改（数字、时间窗、口径的修正）作为奖励信号，风格修改过滤。踩坑二：采纳信号有偏（用户没编辑可能只是没细看）——弱信号降权处理，与勾稽奖励分层组合而不是等权平均。踩坑三：奖励 hacking 风险（策略学会讨好勾稽器而非真做对分析）——奖励组合里保留人工抽检通道做对抗验证。
⑥ 验证与迭代
埋点覆盖率（任务全链路可回放）100%；奖励与人工判断一致率校准【占位：__%】达标后才进 RL 实验；RL 实验以编排基线为对照（完成率 / 勾稽率 / 长尾覆盖）。诚实边界：RL 化处于数据与奖励准备阶段，未生产化——面试如实陈述阶段与下一步。
业界对比
Search-R1 → DeepResearcher → Tongyi DeepResearch 是 RL 化 deep research 的演进三部曲——我们的三步走与这条线的工程节奏对齐。
设计巧思
埋点不是运营工具，是未来 RL 的奖励基建——今天的数据结构决定明天能训什么。

🔥 面试官深挖预演

追问 1
Q：你们的 RL 化做到哪一步了？
A：诚实版回答：环境与动作空间随系统天然就有，奖励通道在建——数字勾稽是天然的 verifier 奖励。这个准备本身就是工程量，而且它反过来提升了编排版的质量（评测更严了）。不上 RL 不是不懂 RL，是基建顺序的清醒。
追问 2
Q：为什么绩效评价的 RL 比开放研究好做？
A：奖励：数字勾稽可自动验证、无歧义；环境：组件 API 确定性强、成本低。开放研究的奖励要人评或弱模型评，我们要的是对账——领域结构决定了 RL 落地难度，这是我选这个场景做深的原因之一。

异常处理 Case 集（高频拷打）

异常 case：组件/数据接口限流（429）
每端点独立令牌桶 + 指数退避重试；持续限流则切换降级路径或标注缺口。经济性权衡：降级是否启用备选计算路径由指标重要性决定，非核心指标直接标缺口。
异常 case：规划出循环依赖（节点 A 依赖 B，B 又依赖 A）
规划输出做 DAG 校验，发现环则合并或拆解重排；重排仍失败则回退到该 skill 的兜底线性流程。
异常 case：关键组件返回空/异常值（勾稽发现归因贡献不闭合）
不编造：该分析维度显式输出'计算异常，待复核'并降级——把失败转化为可见的质检需求，绝不用'看起来合理'的数字补位。
异常 case：并行部分失败导致分析不平衡
缺指标时报告自动降级为'已有指标 + 缺口说明'；用户体验上宁可短不可错。
异常 case：多组合对比时中间结果张冠李戴
黑板句柄带语义描述（节点+内容摘要），拉取前先验匹配；数字类中间结果锁定来源标签（组合 ID + 时点）。
异常 case：工具循环调用（同工具同参数反复调）
状态机防环：计数超 2 次强制跳出，触发节点级失败评估——局部重试还是升级为任务级重规划。
