民生保险知识库平台：10 个可以深挖的维度

怎么用：面试官追问"再深入一点"时，每个维度都是一条独立的防线——Struggle（真实困境）→ 拆解 → 调研测试 → 解决步骤 → 验证 → 效果 → 迭代中新问题与化解 → 业界对比 → 设计巧思。黄色高亮为待填真实数据。

维度 1 · 多知识库体系：按场景切分与路由

深挖维度
价值点：条款问答、佣金规则、产品手册、FAQ 的数据形态与更新频率完全不同——一个库装所有内容必然互相污染。
Struggle
早期单库混装：检索条款问题时混入 FAQ 口水话，佣金规则与产品手册互相干扰，rerank 也救不回。
问题拆解
按'数据形态 × 更新频率 × 权限级别'三个维度切库：条款库（长文档、低频更新、强合规）、佣金规则库（结构化、高频变更）、产品手册库（图文混合）、FAQ 库（短文本、高频迭代）。
调研与测试
调研 Milvus 多 collection + partition 方案、元数据过滤能力、以及 LangChain Router 等多库路由实践。
解决步骤
  • 每库独立 collection + 独立分块策略（条款结构感知 / FAQ 一问一答一条）
  • 意图层输出'目标知识库'标签，检索前路由
  • 跨库问题（先查条款再查佣金）由编排层串联两次检索
验证思路
每库独立 golden set + 跨库问题专项集；对比单库混装与多库路由的准确率/污染率。
达成效果
跨库污染导致的错答基本清零【占位：__】。
迭代新问题
路由错误会把问题送错库 → 化解：意图层输出 Top2 库做并行检索、融合排序，宁多勿错。
业界对比
Morgan Stanley 内部知识库同样是'文档分类 + 权限域'先行；LangChain Router 是同类路由抽象。
设计巧思
切分的本质不是分文件，是分'答案的可信边界'——每库有自己的证据标准与拒答口径。

维度 2 · 权限管控：检索前过滤与越权测试

深挖维度
价值点：佣金、客户数据涉及个人隐私与合规——权限是硬门槛，不是体验优化。
Struggle
早期检索层无权限概念：测试坐席账号能召回其他分支机构的佣金规则片段。
问题拆解
权限拆三层：谁能用这个工具（接口级）、谁能检索这个库（库级）、谁能看这条内容（条级 metadata）。
调研与测试
调研 Milvus 标量过滤（partition_key + boolean expr）、RBAC 模型、金融行业'最小可见'原则。
解决步骤
  • 入库时写入权限元数据（机构/角色/产品线）
  • 检索表达式强制带权限过滤（不可绕过）
  • 接口层再做身份与范围二次校验（双保险）
验证思路
越权测试用例集：跨机构、跨角色、已下线内容，全部应返回空或拒答；纳入发版回归。
达成效果
越权用例通过率 100%【占位：__】；通过合规评审。
迭代新问题
权限过滤降低召回质量 → 化解：权限前置到意图层提示切换角色视角，而非静默过滤。
业界对比
OpenAI × Morgan Stanley 案例：答案只允许来自内部内容——权限域与合规先行是金融 AI 的共识。
设计巧思
权限不是过滤器，是证据的属性——每条证据天生带权限标签。

维度 3 · 数据正确性校验：入库、版本与回流

深挖维度
价值点：知识库的错误是系统性错误——一条错误条款会污染所有相关问答。
Struggle
早期解析偶尔漏表格行、新旧版本条款混存，答案口径随机错误，排查极难。
问题拆解
拆成三道关：入库前（解析质量校验）、入库时（版本管理）、入库后（抽样与回流）。
调研与测试
参考 TAT-QA 对表格结构的标注方式设计解析校验；调研文档版本管理（生效日期/废止标记）的合规要求。
解决步骤
  • 解析校验：表格行列完整性、标题层级树校验、跨页表格拼接检查
  • 版本管理：条款按生效日期双版本共存，检索时按当天日期过滤
  • 抽样：每批次入库后按 5% 人工抽检，错误样本回流解析器迭代
验证思路
解析错误率监控看板 + 每周人工抽检报告；新旧版本答案对比回归。
达成效果
解析类坏例下降【占位：__%】；口径不一致投诉清零。
迭代新问题
抽检人力成本高 → 化解：LLM 预审 + 人工只审低置信样本，抽检成本降约七成【占位】。
业界对比
保险条款的生效/废止管理在监管与行业内都有明确要求——版本化是合规刚需而非技术选择。
设计巧思
正确性校验的哲学：机器做全量初筛，人做低置信复核——人力花在刀刃上。

维度 4 · 意图路由三层体系与阈值调优

深挖维度
价值点：意图是调度中枢：路由错，后面全错。
Struggle
最初用单 LLM 分类：延迟 2s+、月成本高、且不可解释——合规问'为什么路由到办理'答不出。
问题拆解
按'频次 × 风险 × 可解释性'拆：高频意图规则化（零成本毫秒级）、长尾小模型、模糊与新增意图 LLM 兜底。
调研与测试
调研三层路由的行业实践（面经印证这是标准答案）、小模型在保险语料上的准确率、置信度校准方法。
解决步骤
  • 规则层：关键词+正则覆盖 Top 意图
  • 小模型：微调分类，置信度低于阈值落 LLM
  • LLM：few-shot + 意图定义文档，输出带置信度
  • 阈值按意图分别调（高风险意图宁转人工）
验证思路
标注集分层测试（每意图 ≥200 条）+ 线上 A/B：误路由率、转人工率、平均延迟三维。
达成效果
意图 Top1【占位：__%】；平均首响从 2s 降到【占位】ms；月 token 成本降【占位：__%】。
迭代新问题
新意图不断出现，小模型要频繁重训 → 化解：LLM 兜底层先顶，积累 N 条后触发重训，半自动标注。
业界对比
阿里云 PAI 官方意图识别方案与多家保险客服实践都采用分层路由——'换大模型'在面经里是扣分项。
设计巧思
分层路由的精髓：把'不确定性'限制在最贵的那一层，便宜层消化确定性。

维度 5 · 佣金问答：数字不过 LLM

深挖维度
价值点：佣金是销售最关心、最容易引发纠纷的数字——一分钱不能错。
Struggle
最初让 LLM 读佣金规则文档回答计算类问题，出现过规则引用错误和计算幻觉，被业务方一票否决。
问题拆解
拆成'取数'与'解释'两段：数字必须来自系统接口（可审计），解释可以生成。识别'需要计算的问题'（如'年终奖算不算首年佣金'）走规则问答而非实时计算。
调研与测试
FinanceBench（LLM 开卷金融问答错误率高）作为'数字不过 LLM'的学术依据；NL2SQL 方案被否决（权限/口径/审计三关过不了）。
解决步骤
  • 槽位抽取：险种、月份、人员身份（结构化输出）
  • 权限校验：只能查本人/有权限的团队
  • 调佣金系统 API 取数
  • 模板化拼装 + LLM 仅做措辞润色（数字原样透传）
验证思路
数字类专项评测：与系统导出对账，要求 100% 一致；权限越权用例回归。
达成效果
佣金类零算错；纠纷相关工单下降【占位：__%】。
迭代新问题
新业务字段频繁进接口 → 化解：接口返回 schema 版本化，模板按版本渲染。
业界对比
FinanceBench 实证 + Morgan Stanley 案例（答案仅来自内部内容且经评估）共同支撑这一决策。
设计巧思
数字不是生成问题，是查询问题——把 LLM 从'计算者'降级为'转述者'，风险就消灭了。

维度 6 · 保单变更：槽位抽取 + 规则引擎校验

深挖维度
价值点：变更办理是'合规 + 体验'双敏感场景：既要听懂自然语言，又不能让模型决定能不能办。
Struggle
直接让 LLM 判定'能否变更、需要什么材料'，出现过编造规则（'需在 3 天内办理'）与漏判限制条件的严重问题。
问题拆解
拆成'理解'与'判定'两段：LLM 把自然语言抽成结构化变更请求（JSON schema：险种/变更项/新值/关系），规则引擎按险种规则校验可行性并输出标准理由文本。
调研与测试
调研 function calling / 结构化输出（JSON schema 约束）最佳实践；与业务方共建规则库（可变更项矩阵）。
解决步骤
  • LLM 结构化抽取（schema 校验，失败重试并降级澄清追问）
  • 规则引擎逐条校验并给出标准理由文本
  • 不可办理时给出替代方案与依据条款
验证思路
抽取字段准确率（人工标注对照）；规则判定与业务专家一致率抽检；端到端回归集。
达成效果
抽取准确率【占位：__%】；规则判定与业务一致率 100%（规则引擎保证）。
迭代新问题
用户表述模糊（'改成我老婆'未指明保单）→ 化解：多保单命中时反问澄清，不猜。
业界对比
金融行业通行做法：判定与执行走确定性系统，LLM 只做理解层——监管口径一致。
设计巧思
LLM 负责'听懂'，规则负责'决定'——职责分离让两边都做各自最擅长的事。

维度 7 · 幻觉五层治理

深挖维度
价值点：幻觉是保险场景的合规生死线：一个编造的免责条款可能引发监管问题。
Struggle
上线初期幻觉率不可度量，业务方反馈'有时对有时编'，无法定位是检索问题还是生成问题。
问题拆解
按来源分三类（检索错 / 知识缺 / 生成倾向），每类不同解法；再按链路分五层布防：检索 / 生成 / 校验 / 产品 / 评测。
调研与测试
调研 RAG 幻觉缓解研究（CRAG/Self-RAG 思路）、FinanceBench 错误分布、行业拒答实践。
解决步骤
  • 检索层：混合检索+rerank 提高证据质量
  • 生成层：grounded prompt + few-shot 拒答示例 + 低温度
  • 校验层：引用溯源，无源句不展示；数字类二次核对
  • 产品层：拒答即 feature + 转人工
  • 评测层：幻觉专项评测集分类别度量
验证思路
幻觉评测集（三类来源标注）自动跑 + LLM-as-judge 抽检 + 人工月度抽检对齐 judge。
达成效果
幻觉率从不可知变为可度量：分类别幻觉率【占位：__%】，整体压至门槛以下。
迭代新问题
拒答率过高影响体验 → 化解：阈值分层 + 拒答后相似问题推荐 / 转人工。
业界对比
FinanceBench 实证 LLM 开卷金融 QA 错误率高；Self-RAG/CRAG 提供检索自反思的学术路线。
设计巧思
幻觉治理的哲学：机器做全量防御，产品做残余兜底，度量贯穿始终。

维度 8 · 评测体系分层与'难找易验'

深挖维度
价值点：没有度量就没有优化：评测体系是整个平台最值钱的资产。
Struggle
评测集全是简单单跳题，模型刷分很高但线上多跳问题频频失败——评测与真实分布脱节。
问题拆解
按难度（单跳/多跳/无答案）× 类别（条款/佣金/变更）交叉分层；每题带证据链标注与验收口径。
调研与测试
BrowseComp 的'难找易验'原则（多跳难找但答案可客观核对）；BFCL V3 的 irrelevance 维度。
解决步骤
  • 分层扩容 golden set
  • 无答案类专门考察拒答
  • 每题标注证据链支持事后审计
  • 线上坏例按分层归类回流
验证思路
评测集与线上 badcase 分布一致性对比；人工抽检对齐率。
达成效果
评测结果首次能预测线上表现；发版门禁由人审变为数据审。
迭代新问题
评测集变大后回归变慢 → 化解：分层抽样回归 + 变更相关层全量跑。
业界对比
BrowseComp（OpenAI）与 BFCL V3（UC Berkeley）是评测设计的两个参照系：前者学难度设计，后者学维度拆分。
设计巧思
评测集是公司的资产：它沉淀了'什么算对'的业务共识。

维度 9 · 冷启动与数据埋点：没有用户数据时怎么迭代

深挖维度
价值点：上线初期没有行为数据，优化无从下手——这是所有 toB AI 产品的共同困境。
Struggle
上线前两周：无点击数据、无负反馈，唯一信号是'客户没投诉'，优化方向全靠猜。
问题拆解
拆成'能自动采集什么、能代理什么、能主动要什么'：①埋点事件（query/意图/检索命中/引用率/响应时长）②代理满意度指标（转人工率、复问率、会话放弃率）③主动获取（每周业务方评审会、灰度问卷）。
调研与测试
调研 toB 客服类产品的满意度代理指标体系；与业务方确认'什么信号代表回答真的好'。
解决步骤
  • 全链路事件埋点：从 query 进来到返回的每一步（意图结果、检索条数、rerank 分、生成耗时）
  • 会话级点赞/点踩 + 原因勾选
  • 每周输出'零引用答案清单'（无条款依据的回答人工复核）
  • badcase 评审会：业务方+工程共同定性
验证思路
埋点数据与人工抽样判断的一致性校验；代理指标与业务方主观满意度的相关性回测。
达成效果
上线一个月即积累【占位：__】条真实 query，识别出【占位：__】类系统性问题进入迭代。
迭代新问题
点踩率低不等于满意（用户可能直接弃用）→ 化解：把'复问率/放弃率'纳入，多信号交叉。
业界对比
行业共识：智能客服解决率 90%+ 是标杆口径（平安/阳光），但'解决'的定义必须与业务方书面约定。
设计巧思
toB 的满意度不在点击里，在'用户下次还来问'里。

维度 10 · 上下文超限：提示词的压缩与裁剪

深挖维度
价值点：多轮对话 + 多证据引用必然撑爆窗口：压缩策略直接决定成本与质量。
Struggle
多轮场景到第 8~10 轮上下文超限，早期粗暴截断最早对话——用户说'我刚才说的不算，改成…'时模型失忆，体验崩塌。
问题拆解
按'信息的时效与价值'分五级：系统规则（永不动）> 当前任务状态（必须保）> 近期对话（全保）> 早期对话（摘要）> 检索证据（按相关度裁剪）。
调研与测试
调研 Manus 的 append-only + 文件句柄、LangGraph 的 checkpoint 思想、摘要压缩的坑（关键约束被摘要掉）。
解决步骤
  • 分级裁剪：系统规则与当前任务状态永不裁剪
  • 早期对话滚动摘要（保留结论与承诺，丢弃过程）
  • 检索证据按 rerank 分数截断 + 引用句柄化
  • 约束类信息（'我说的不算，改成…'）显式写入状态区，不参与摘要
验证思路
多轮一致性评测集（第 N 轮还能否引用第 2 轮的约束）+ 关键信息保留率人工评估。
达成效果
多轮约束保持率【占位：__%】；单会话输入 token 下降【占位：__%】。
迭代新问题
摘要本身耗时耗钱 → 化解：阈值触发（超限才摘要）+ 增量摘要（只摘新增段）。
业界对比
LangGraph checkpoint / Manus 文件系统 / Mem0 记忆库是业界三种代表解法，对应'状态落库 / 句柄化 / 记忆蒸馏'。
设计巧思
压缩不是丢信息，是把信息分层放置：约束进状态区、过程进摘要、证据进句柄。

异常处理 Case 集（高频拷打）

异常 case：工具调用失败（佣金接口 5xx/超时）
重试分级：接口超时 3s 重试 1 次（幂等查询）；仍失败则降级为'系统繁忙，已记录，稍后回复'并生成待办工单——绝不编造数字。业务上把'如实说拿不到'定义成正确行为。
异常 case：实体解析失败（用户说'把我那份保单改了'但命中多张保单）
不猜。反问澄清：列出候选保单让用户选择；单保单但变更项模糊时给'你想变更哪一项'菜单。原则：办理类动作宁可多一轮澄清。
异常 case：工具循环调用（A 工具结果触发再调 A）
状态机防环：同一工具同参数连续调用计数，超 2 次强制跳出并转人工/澄清；步数预算上限 12 步。
异常 case：LLM 输出不合法 JSON（抽取失败）
schema 校验失败 → 带错误信息重试一次（把校验错误回喂）→ 再失败走澄清追问模板；绝不静默吞掉，因为下游规则引擎需要合法入参。
异常 case：检索空结果
三级降级：①放宽（同义改写/去掉产品限定词）重检 ②跨库检索 ③仍空则明确拒答'知识库暂未覆盖'并转人工，同时记录为知识缺口需求。
异常 case：拒答被业务方投诉'太保守'
阈值分层与数据化：按意图与风险等级配不同阈值，每季度用人工标注校准'该答未答/不该答乱答'的混淆矩阵。
