民生保险知识库平台：10 个可以深挖的维度

怎么用：面试官追问"再深入一点"时，每个维度都是一条完整的防线，按六步方法论展开——① 问题定义（把症状翻译成可度量的工程问题）→ ② 问题分析（根因链 + 排除的假设与证据）→ ③ 问题场景（具体现场与复现方式）→ ④ 方案对比（三个候选的优劣与结论）→ ⑤ 采用与踩坑（第一版怎么翻车、怎么改）→ ⑥ 验证与迭代（指标、回归、后续演进）。红色"面试官深挖预演"是站在面试官视角的追问与亮点回答。黄色高亮为待填真实数据。

维度 1 · 多知识库体系：按场景切分与路由

深挖维度
价值点：条款问答、佣金规则、产品手册、FAQ 的数据形态与更新频率完全不同——一个库装所有内容必然互相污染。
① 问题定义
症状是三类“串味”：条款问题混入 FAQ 口水话、佣金规则与产品手册互相干扰、rerank 之后依然串。把它定义成可度量的工程问题：检索返回 Top5 中含错误知识域片段的比例记为跨域污染率，灰度抽测约 18%【占位：__%】；进一步归因，错误答案里约四成能追溯到跨域污染。边界也要说清：这不是“检索排序不够好”——换更强 rerank 只降 3 个百分点，说明问题在库的结构而不在排序。
② 问题分析
排除法走三步：假设一 rerank 太弱，换强模型改善有限，排除主因；假设二分块太碎，单库内调整分块粒度无改善，排除；假设三 embedding 域适应差，换保险语料微调的向量模型略有改善但串味依旧。真正的根因：条款、FAQ、手册都是“保险话术”，语言风格天然相近，向量空间里本来就贴在一起——单库检索根本没有“域”的概念，它不知道自己不知道边界。
③ 问题场景
典型现场：坐席问“XX 重疾的等待期是 90 天还是 180 天”，Top5 里 3 条条款 2 条 FAQ，FAQ 那句“90 天”是老产品口径——答案新旧口径混着说，坐席拿去答复客户就是事故。可复现：构造 20 道“条款 vs FAQ 口径冲突”探针题，单库模式下稳定复现串味。
④ 方案对比
方案优势劣势/风险结论
单库 + 域元数据过滤改动最小，一个索引管所有分块/嵌入参数只能全库折衷；索引重建互相影响；域仍是“逻辑分区”不是物理边界否
多 collection 分库 + 意图路由每库独立分块策略（条款结构感知 / FAQ 一问一答）、独立索引参数；污染被物理隔离；可独立迭代与回归路由错一次答案就全错；collection 与运维面翻倍采用
主域分库 + 小域合并（混合）折中，减少 collection 数小域之间又开始互相干扰，回到原点否
⑤ 采用与踩坑
最终采用四库分立（条款 / 佣金规则 / 产品手册 / FAQ）+ 意图层输出目标库标签、检索前路由。踩坑一：路由错误是单点放大器——补上 Top2 库并行检索 + 融合排序，宁多勿错，串味率再降且召回回升约 6 个百分点【占位：__】。踩坑二：跨库问题（先查条款再核佣金规则）只能选一库——编排层支持两跳串联检索。踩坑三：FAQ 库高频重建索引引发线上抖动——改成蓝绿双索引原子切换。
⑥ 验证与迭代
每库独立 golden set + 20 道跨库口径冲突探针集纳入回归；单库混装 vs 多库路由 A/B 对比：跨域污染率从约 18% 压到 2% 以下【占位：__%】。迭代机制：新知识接入走“数据形态 × 更新频率 × 权限级别”三判定 checklist，把“先塞进现有库再说”这种冲动挡在流程外。
业界对比
Morgan Stanley 内部知识库同样是“文档分类 + 权限域”先行；LangChain Router 是同类路由抽象。
设计巧思
切分的本质不是分文件，是分“答案的可信边界”——每库有自己的证据标准与拒答口径。

🔥 面试官深挖预演

追问 1
Q：为什么不一个库加 metadata 过滤，省得路由？
A：过滤解决的是查回来之后的权限与版本问题，解决不了分块与索引参数被全库平均的问题——条款要结构感知分块、FAQ 一条一问，同一套参数必然两头不讨好。分库本质是把参数自由度还给每个域，过滤和分库是两层正交的事。
追问 2
Q：路由错了怎么办，错误的代价你接受吗？
A：路由错误的代价被两层兜住：Top2 库并行检索保证召回不丢，rerank 融合排序保证错选的库排不进上下文。我们把路由错误从'答案错'降级成'排序问题'——这是可度量可优化的。
追问 3
Q：库多了运维和回归成本呢？
A：蓝绿切换解决重建抖动；每库独立 golden set 反而让回归更快——变更影响面从全库缩小到单库，回归集合小了、归因清楚了。

维度 2 · 权限管控：检索前过滤与越权测试

深挖维度
价值点：佣金、客户数据涉及个人隐私与合规——权限是硬门槛，不是体验优化。
① 问题定义
问题的发现方式很不体面：测试坐席账号检索“续期佣金比例”，返回集里出现了浙江分公司的规则片段。精确定义为“检索可见性越权率”——无权限文档出现在返回集的比例，抽测非零即不合格。这是合规一票否决项：不是“优化项”，是“不上线项”。影响面评估：涉及跨机构规则文档、已下线产品、客户数据三类越权面。
② 问题分析
三层拆解后定位：接口级（谁能调这个能力）、库级（谁能查哪个库）、条级（谁能看哪条内容）。早期只做了接口鉴权，检索层是裸奔的——根本原因是检索系统天然只有“相关性”概念没有“可见性”概念，权限必须作为数据的属性注入而不是调用方的自觉。另一个被排除的假设是“入库时漏了机构字段”——字段在，但检索表达式根本没带过滤条件。
③ 问题场景
现场还原：坐席 A（上海）问“浙江团队的续期佣金比例怎么算”，向量检索按语义召回浙江规则文档，生成层若无其事引用——答案技术上“正确”，权限上已经泄露。复现方式：低权限账号跑 50 条跨机构探针 query，统计越权返回。
④ 方案对比
方案优势劣势/风险结论
检索后过滤（先查再滤）实现简单，索引统一过滤前文档已进服务内存与日志，“查得到”本身就是泄露面；TopK 过滤后可能剩 0 条，把权限问题劣化为检索质量问题否
检索前过滤（表达式强制注入）权限成为检索条件，无权限的数据物理不可见；与库级权限正交组合入库必须带全权限标签，标签错了就是事故；权限组合爆炸需控制粒度采用
权限域物理分 collection隔离最彻底机构 × 角色 × 产品线的组合让 collection 数爆炸，不可运维否
⑤ 采用与踩坑
采用：入库写入权限元数据（机构 / 角色 / 产品线）+ 框架层统一拼接权限过滤表达式——注意是框架层注入，业务代码不可绕过、也拿不到“不过滤”的接口。踩坑一：权限标签靠人工维护，组织架构一调整标签就过期——改为与 HR 系统定时同步 + 变更审计流水。踩坑二：静默过滤导致“明明该查到却查不到”，坐席困惑——意图层前置角色视角提示，检索不足时提示“当前权限范围未覆盖，可申请扩展”而不是空结果。踩坑三：权限过滤与召回率此消彼长——把“权限命中不足”作为独立信号上报，区分“真没有”和“看不到”。
⑥ 验证与迭代
越权用例集（跨机构 / 跨角色 / 已下线内容）纳入发版回归，通过率必须 100%，任何一条失败阻断发版；季度红队渗透抽测。上线后越权事故为零【占位：__】。
业界对比
OpenAI × Morgan Stanley 案例：答案只允许来自内部内容——权限域与合规先行是金融 AI 共识。
设计巧思
权限不是过滤器，是证据的属性——每条证据天生带权限标签。

🔥 面试官深挖预演

追问 1
Q：检索后过滤不行吗？反正用户也看不到？
A：不行。过滤之前文档已经进入服务内存、日志、监控，“查得到”本身就是泄露；而且 TopK 过滤后可能剩零条，用户感知是“系统坏了”。检索前过滤让权限成为物理不可见，这两者的安全等级完全不同。
追问 2
Q：权限标签本身错了怎么办？
A：三重兜底：框架统一注入保证没有绕过路径、HR 系统同步保证标签新鲜、越权回归用例保证变更不引入漏洞。标签变更走审计流水，可回溯到人。

维度 3 · 数据正确性校验：入库、版本与回流

深挖维度
价值点：知识库的错误是系统性错误——一条错误条款会污染所有相关问答。
① 问题定义
症状极具迷惑性：同一个问题昨天和今天答案不一样，像“灵异问题”。定义为入库质量缺陷率——抽检样本中解析错误（漏表格行 / 层级错 / 跨页拼接错）的比例；叠加版本混存缺陷——新旧条款同时在库，检索不区分生效日期。影响：错误是系统性的，一条坏数据污染所有命中它的问答，而向量检索让你无法预知“哪些问题会被命中”，排查半径极大。
② 问题分析
两类根因分开治：解析缺陷集中在三类（表格漏行约一半、标题层级树断裂、跨页表格拼接错位），是长尾但可聚类的；版本缺陷是流程缺失——入库只管“进”，没有“该谁生效”的概念。为什么难排查：症状出现在问答端，根因在数据端，中间隔了向量化与检索两层，坏例只能靠人工逆向追到源文档。排除的假设：“模型变笨了”——同一题复测答案漂移，且不同模型都漂，锁定数据侧。
③ 问题场景
现场：2024 版条款 3 月 1 日生效，旧版未下架。3 月 5 日坐席问“等待期多久”，检索混回新旧两版片段，模型各引用一半。复现：构造 30 道“版本敏感问题”（新旧行为不同的条款点），稳定复现混引。
④ 方案对比
方案优势劣势/风险结论
人工全量校验最可靠条款文档上千份、每次更新都来一遍，成本不可行否
解析置信度 + 人工抽检 + LLM 预审机器全量初筛、人只看低置信样本，成本与覆盖平衡置信度模型本身要调优；LLM 预审有误判，需要抽检对齐采用
版本：新版本直接覆盖旧版实现最简单不可回溯、不可审计，监管检查一问就死否（改为双版本共存 + 生效日期过滤）
⑤ 采用与踩坑
采用：解析侧三道关（表格行列完整性校验 / 标题层级树校验 / 跨页拼接检查）+ 5% 人工抽检；版本侧双版本共存、检索按当天日期过滤生效版本。踩坑一：解析校验规则越写越多成“规则地狱”——按错误类型聚类后聚焦 Top3 类型专项修复，覆盖八成缺陷，其余交给抽检回流。踩坑二：5% 抽检仍有漏网且人力贵——引入 LLM 预审（对解析结果做一致性自检，如“表格行列乘积与单元格数是否一致”），人工只审低置信样本，抽检成本降约七成【占位：__%】。踩坑三：版本过滤上线后旧问题“突然查不到”——按 query 时间与文档生效日期双过滤，并在答案里声明口径版本。
⑥ 验证与迭代
解析错误率看板周更；30 道版本探针纳入回归；口径不一致投诉清零【占位：__】。迭代：错误样本自动回流解析器迭代队列，形成“线上坏例 → 数据缺陷 → 解析器修复 → 回归验证”闭环。
业界对比
保险条款的生效/废止管理在监管与行业内都有明确要求——版本化是合规刚需而非技术选择。
设计巧思
正确性校验的哲学：机器做全量初筛，人做低置信复核——人力花在刀刃上。

🔥 面试官深挖预演

追问 1
Q：为什么不直接上最强的文档解析模型？
A：强解析解决不了版本与权限这类元数据问题——那不是“看不懂文档”，是“流程没有生效日期的概念”。而且解析错误是长尾分布，规则+置信度+抽检回流的性价比远高于换模型；模型再强也要这三道关兜底。
追问 2
Q：怎么保证抽检本身不漏？
A：抽检是兜底不是主力：机器做全量初筛（规则+LLM 预审），人只做低置信复核；线上坏例再逆向回流。三层任何一层接住都行，单层漏掉不致命。

维度 4 · 意图路由三层体系与阈值调优

深挖维度
价值点：意图是调度中枢：路由错，后面全错。
① 问题定义
把“感觉慢、感觉贵、说不清”翻译成三个可度量的问题：平均首响 2s+（目标 500ms 内）、月 token 成本高企【占位：__】、合规审计问“为什么这句被路由到办理类”时拿不出规则级依据。边界：这是单 LLM 分类方案的系统性问题，不是调 prompt 能救的——同一套方案调优两周，三项指标都没有数量级改善。
② 问题分析
流量分布分析给出关键洞察：Top5 意图占约七成流量【占位：__%】——大部分请求根本不配用 LLM 分类，是“用大炮打蚊子”。成本与延迟高度集中在低价值判断上。而可解释性问题的根因是：LLM 分类是黑盒概率，合规需要的是“命中了哪条规则”的确定性依据。三个问题指向同一个解：把请求分层，确定性高的走便宜层，不确定性留给 LLM。
③ 问题场景
现场：早高峰坐席连续问高频问题（“XX 产品佣金多少”“等待期多久”），每个都过一遍 LLM 分类，首响堆到 2s+，坐席等不及直接关掉——转化率肉眼可见地掉。复现：压测脚本模拟 50 QPS 高频意图流量，单 LLM 层 P99 超 3s。
④ 方案对比
方案优势劣势/风险结论
全 LLM few-shot 分类（基线）实现快、新意图零成本延迟秒级、token 成本线性涨、不可解释否（保留为兜底层）
规则 + LLM 两层高频意图毫秒级零成本中部意图（表述多变的高频类）规则覆盖不住，仍大量落入 LLM否
规则 + 小模型 + LLM 三层频次 × 风险 × 可解释性三维最优；中部意图由微调小模型毫秒级接住小模型要标注与重训；置信度需要校准采用
⑤ 采用与踩坑
采用三层：规则层（关键词+正则覆盖 Top 意图）、小模型层（微调分类器接中部）、LLM 兜底层（长尾与新增意图，few-shot + 意图定义文档，输出带置信度）。踩坑一：规则层写贪了——覆盖冲到 85% 后关键词开始互相冲突，误路由率抬头；回撤到七成覆盖，模糊区明确交给小模型。踩坑二：小模型置信度未校准——标称 0.9 置信的实际准确率只有 0.7，直接用原始分数设阈值全错；做温度缩放校准后分数才有意义。踩坑三：办理类等高风险意图误路由代价大——阈值按意图分级设置，高风险宁转人工，不追求统一的“最优阈值”。
⑥ 验证与迭代
分层标注集（每意图 200+ 条）离线评测 + 线上 A/B 三维观测（误路由率 / 转人工率 / 首响延迟）。结果：意图 Top1 提升至【占位：__%】，平均首响从 2s 降到【占位：__】ms，月 token 成本降约八成【占位：__%】。迭代：新意图先由 LLM 兜底层顶住并落盘，积累 N 条自动触发小模型重训（半自动标注），形成“新意图冷启动 → 进化到便宜层”的流水线。
业界对比
阿里云 PAI 官方意图识别方案与多家保险客服实践都采用分层路由——“换大模型”在面经里是公认扣分项。
设计巧思
分层路由的精髓：把“不确定性”限制在最贵的那一层，便宜层消化确定性。

🔥 面试官深挖预演

追问 1
Q：为什么不直接用最强的大模型 few-shot 分类，一步到位？
A：三个量都不答应：延迟（秒级 vs 毫秒级）、成本（七成流量不配用 LLM）、可解释性（合规要规则依据，LLM 给不了）。分层路由的精髓是把不确定性限制在最贵的那一层——便宜层消化确定性，这是成本工程的架构级解法。
追问 2
Q：阈值怎么定的？拍脑袋吗？
A：不是全局一个数：先做置信度校准（温度缩放让分数可信），再按意图的风险等级分别定阈值——办理类宁转人工，闲聊类宁放行。用混淆矩阵按季度重校，阈值是运营参数不是玄学。
追问 3
Q：三层之间的边界会漂移吧？
A：会，所以有“进化流水线”：LLM 兜底层落盘的新意图样本积累到阈值就触发小模型重训，边界是动态移动的，方向永远是“把流量从贵层往便宜层搬”。

维度 5 · 佣金问答：数字不过 LLM

深挖维度
价值点：佣金是销售最关心、最容易引发纠纷的数字——一分钱不能错。
① 问题定义
最初方案让 LLM 读佣金规则文档回答计算类问题，业务方评审时一票否决。把否决理由工程化：错误分三类——引用错规则（检索问题）、理解错规则（推理问题）、算错数字（计算问题）。前两类可以优化，第三类没有“可接受错误率”这个概念：佣金算错一分钱就是纠纷，算错一次就摧毁信任。问题定义：如何让数字类答案达到系统级精度（与源系统完全一致）。
② 问题分析
关键认知转折：数字答案的本质不是“生成”而是“查询”。佣金数据在源系统里是精确存在的——应收多少、实发多少、何时发放，都是确定性数据。让 LLM 去算，等于引入一个不必要的概率环节去回答一个本该确定的问题。被否掉的 NL2SQL 路线分析：权限（生成的 SQL 绕过应用层权限模型）、口径（SQL 里的统计口径无法受控）、审计（没人能审一段生成的 SQL）三关都过不了。
③ 问题场景
现场：坐席问“我 12 月的保单什么时候开始返续期佣金”，模型把“第 13 个保单年度起”理解成“次年 12 月”——规则歧义 + 日期计算双重出错。复现：50 道计算类探针，错误率约 8%【占位：__%】，且错误形态分布三类都有。
④ 方案对比
方案优势劣势/风险结论
更强模型 + CoT 推理覆盖面广错误率只能压低不能归零；计算链越长错得越隐蔽否——底线不过
NL2SQL 直查灵活权限 / 口径 / 审计三关全挂否
槽位抽取 + 系统接口取数 + 模板拼装数字精度=源系统精度，天然带权限，全程可审计只覆盖模式化问题；长尾解释类问题要分流采用
⑤ 采用与踩坑
采用四步链路：槽位抽取（险种 / 月份 / 人员身份，结构化输出）→ 权限校验（只能查本人或有权限的团队）→ 调佣金系统 API 取数 → 模板化拼装（数字原样透传，LLM 只做措辞润色且数字锁定不可改写）。踩坑一：槽位抽取不齐（月份、身份缺）时模型倾向猜默认值——改为澄清追问，宁可多一轮。踩坑二：接口 schema 变更导致模板渲染错位——接口返回带版本号，模板按版本渲染 + 契约测试。踩坑三：“为什么我的佣金是这么多”这类解释型问题被误判为计算型——意图再细分：计算类走 API，解释类走规则 RAG，两类链路分治。
⑥ 验证与迭代
数字类专项评测：与佣金系统导出对账，要求 100% 一致（这是硬门槛不是统计指标）；越权用例回归；纠纷相关工单下降【占位：__%】。迭代：新模式化问题（如团体单佣金）按四步链路模板化扩展，成本以天计。
业界对比
FinanceBench 实证 LLM 开卷金融 QA 错误率高；Morgan Stanley 案例（答案仅来自内部内容且经评估）支撑同一决策。
设计巧思
数字不是生成问题，是查询问题——把 LLM 从“计算者”降级为“转述者”，风险就消灭了。

🔥 面试官深挖预演

追问 1
Q：让 LLM 算完再用规则校验一遍不行吗？
A：校验的前提是有正确答案可对——正确答案从哪来？还得查源系统。既然查了，LLM 再算一遍就是引入一个不必要的风险源。把 LLM 从“计算者”降级为“转述者”，数字原样透传，风险类型直接消灭，这比“降低风险”高一个层级。
追问 2
Q：这套只适合模式化问题吧，长尾怎么办？
A：对，所以意图层先分诊：模式化的计算类走接口链路（占大头），解释类走规则 RAG，真正的长尾对话才给生成留空间。分诊错了怎么办——解释类问题里出现数字时同样走数字锁定透传，原则是全局的，不是链路局部的。

维度 6 · 保单变更：槽位抽取 + 规则引擎校验

深挖维度
价值点：变更办理是“合规 + 体验”双敏感场景：既要听懂自然语言，又不能让模型决定能不能办。
① 问题定义
早期直接让 LLM 判定“能否变更、需要什么材料”，出现两类严重问题：编造规则（“需在 3 天内办理”——规则里根本没有）与漏判限制条件（该险种受益人变更有范围限制）。定性：判定错误与佣金算错同级——每一次编造规则都是合规事故，没有错误率容忍空间。问题定义：让自然语言进入、让确定性判定出来，中间的翻译层如何设计。
② 问题分析
根因是职责错配：把“决定权”交给了概率模型。LLM 擅长的是把非结构化语言映射到结构化语义（抽取），不擅长的是承担确定性责任（判定）。抽取错误是可检测的（schema 校验不过、字段缺失可追问），判定错误是不可检测的（用户不知道规则是什么，无法发现模型在编）。把错误从不可检测区移到可检测区，是架构级的风险治理。
③ 问题场景
现场：用户说“把受益人改成我女朋友”，模型回答“可以，请提供身份信息”——但该险种受益人范围规则要求未领证配偶需提供关系证明，且某些产品受益人变更有次数限制。模型不知道也没查，一次合规风险就这么产生。复现：30 道含隐藏限制条件的变更请求探针，纯 LLM 判定漏判率过半【占位：__%】。
④ 方案对比
方案优势劣势/风险结论
大模型 + 规则文档 RAG 判定实现快判定仍是概率行为，编造与漏判无法根除否
LLM 抽取 + 规则引擎判定判定确定性 100%、可审计、规则可随监管更新需要把业务规则数字化（与业务共建规则库）；抽取层要兜错采用
全人工办理零风险体验倒退回客服热线，项目价值归零否
⑤ 采用与踩坑
采用：LLM 把自然语言抽成结构化变更请求（JSON schema 约束：险种 / 变更项 / 新值 / 关系），规则引擎按险种规则矩阵校验可行性并输出标准理由文本（附条款原文引用）。踩坑一：抽取 JSON 不合法或字段缺失——schema 校验失败后把错误信息回喂重试一次，再失败走澄清追问模板，绝不静默吞掉。踩坑二：与业务专家共建规则库时“规则数字化”丢语义——规则条目强制带条款原文，输出理由时引用原文而不是转述。踩坑三：多保单歧义（“我那份保单”命中多张）——反问让用户选，不猜；歧义处理是产品原则不是技术细节。
⑥ 验证与迭代
抽取字段准确率人工标注对照【占位：__%】；规则判定与业务专家一致率 100%（规则引擎保证，抽检验证规则库本身）；端到端回归集覆盖每类变更规则。迭代：监管口径变化时只改规则库不发版——规则变更走评审，把合规更新的响应时间从周级压到天级。
业界对比
金融行业通行做法：判定与执行走确定性系统，LLM 只做理解层——监管口径一致。
设计巧思
LLM 负责“听懂”，规则负责“决定”——职责分离让两边都做各自最擅长的事。

🔥 面试官深挖预演

追问 1
Q：LLM 抽取也会错，凭什么信任它？
A：关键不是“不出错”而是“错了能不能被发现”：抽取错误会被 schema 校验和澄清追问拦住（可检测），判定错误用户根本无从发现（不可检测）。架构上把风险从不可检测区挪到可检测区，这是比“提升准确率”更本质的治理。
追问 2
Q：规则库维护成本谁出？
A：规则库是业务资产，与业务方共建、每次监管口径变化走评审。这笔成本买的是“零编造规则”和审计合规——出一次合规事故的成本够维护规则库好几年。

维度 7 · 幻觉五层治理

深挖维度
价值点：幻觉是保险场景的合规生死线：一个编造的免责条款可能引发监管问题。
① 问题定义
上线初期最棘手的不是幻觉本身，是“幻觉率不可度量”——业务方反馈“有时对有时编”，无法定位是检索问题还是生成问题，优化无从下手。问题定义分两步：先建立度量（幻觉率按来源分类统计），再分层治理。不度量就治理等于蒙眼开炮。
② 问题分析
先归因再动手：抽样 100 条幻觉案例人工分类，四类来源——检索没召回、召回了但没排进上下文、上下文有但模型没引用、知识库里根本没有（硬答）。四类占比【占位：__%】直接决定治理优先级：检索类先修检索，知识缺失类先建拒答，生成倾向类才轮到调 prompt。这一步避免了大量无效的 prompt 调优。
③ 问题场景
最危险的现场：坐席问“甲状腺结节 2 级能买 XX 重疾吗”，条款里没有明确除外表述，模型基于“医学常识”合成了一个除外条款——知识缺失型幻觉，语气笃定、看起来专业，杀伤力最大。复现：知识库外问题探针集，统计硬答率。
④ 方案对比
方案优势劣势/风险结论
只调 prompt（拒答指令 + few-shot）成本最低对所有来源一刀切，拒答率暴涨伤体验，且对检索类幻觉无效否（只作为生成层一环）
五层布防：检索 / 生成 / 校验 / 产品 / 评测每层对一类来源设防，可度量可归因工程量大，需要持续运营采用
换更强的模型省事强模型幻觉率低但不为零，且无法给出合规需要的确定性否
⑤ 采用与踩坑
五层：检索层（混合检索 + rerank 提高证据质量）、生成层（grounded prompt + 拒答 few-shot 示例 + 低温度）、校验层（引用溯源——无源句不展示；数字类二次核对）、产品层（拒答即 feature：转人工 + 相似问题推荐）、评测层（幻觉专项集分类别度量）。踩坑一：只上生成层拒答指令时拒答率从 5% 涨到 15%，业务投诉“太保守”——阈值按意图与风险分层，闲聊类放宽、条款类从严。踩坑二：LLM-as-judge 与人工判断初期一致率仅七成——judge 用人工金标校准、错误样本回喂，一致率达标后才准进流程。踩坑三：数字幻觉与事实幻觉混在一个指标里失真——拆开：数字类零容忍走校验器，事实类走引用率统计。
⑥ 验证与迭代
幻觉评测集（三类来源标注）自动回归 + 月度人工抽检对齐 judge；分类别幻觉率进看板：检索类 / 缺失类 / 生成类分别压至门槛以下【占位：__%】。迭代：每类来源的占比变化驱动下一轮投入方向——指标是导航不是装饰。
业界对比
FinanceBench 实证 + Self-RAG/CRAG 提供检索自反思的学术路线；拒答设计是行业共识。
设计巧思
幻觉治理的哲学：机器做全量防御，产品做残余兜底，度量贯穿始终。

🔥 面试官深挖预演

追问 1
Q：幻觉能彻底消灭吗？
A：不能，但可以变成可度量、可归因、可兜底的工程问题。我们把“感觉它编了”变成“哪一层漏了”——每类幻觉有 owner、有指标、有对策。面试里敢说“不能消灭”反而是加分的诚实，后面紧接治理框架就是亮点。
追问 2
Q：拒答率高了业务方不满意怎么办？
A：拒答是 feature 不是 bug——编一个像模像样的答案比拒答危险得多。关键是阈值分层（按风险等级）和拒答体验（转人工 + 相似问题推荐），把“拒答”从死胡同变成分流入口。

维度 8 · 评测体系分层与“难找易验”

深挖维度
价值点：没有度量就没有优化：评测体系是整个平台最值钱的资产。
① 问题定义
症状：评测集跑分 90+，上线后多跳问题频频失败——“评测分数无法预测线上表现”。定义为分布错配问题：线上 badcase 里多跳、口径冲突、无答案类占比约六成【占位：__%】，评测集里这三类几乎为零。评测集考的是模型会的，不是用户问的。
② 问题分析
对线上 badcase 抽样归类发现分布长这样：单跳事实题（评测集全覆盖）只占四成，多跳对比题、版本口径题、无答案题才是大头——而这三类恰好是最难标注的，所以最初建集时被系统性回避了。根因不是偷懒，是“什么算对”在这三类题上没有书面定义：多跳题中间错了算不算对？口径冲突答新版算不算错？没答案该拒答还是该猜？——没有验收口径就没法标注。
③ 问题场景
现场：回归全绿信心满满上线，坐席第一周就问出“XX 产品对比 YY 产品在轻症赔付上的差异”——两跳 + 表格对比 + 口径对齐，评测集里没有这一类，线上直接翻车。复现：把线上 badcase 按类映射回评测集，覆盖率一目了然。
④ 方案对比
方案优势劣势/风险结论
继续加题不分类数量好看分布错配依旧，分数继续骗人否
难度 × 类别交叉分层扩容 + 证据链标注分数恢复预测力；坏例可归因到层标注成本高，验收口径要先与业务书面约定采用
纯线上 A/B 代替离线评测最真实迭代慢、无法归因、坏体验直接伤害用户否（作为补充）
⑤ 采用与踩坑
采用：按难度（单跳 / 多跳 / 无答案）× 类别（条款 / 佣金 / 变更）交叉分层扩容，每题标注证据链与验收口径；无答案类专项补充（对应 BFCL V3 的 irrelevance 维度——该拒的拒）。踩坑一：标注“什么算对”反复吵架——验收口径写进标注规范文档，业务方签认，争议 case 进仲裁池周会裁决。踩坑二：评测集膨胀后回归从 20 分钟涨到 2 小时——分层抽样回归：默认跑变更相关层全量 + 其余层抽样，全量回归留发版前。踩坑三：评测题泄漏进 prompt 迭代过程——评测集分 dev/holdout 双集，迭代只看 dev，holdout 只在里程碑跑。
⑥ 验证与迭代
评测分与线上表现的相关性回测（这是评测集的有效性证明）；发版门禁从人审改为数据审（分层数据达标才放行）；线上坏例按层回流——评测集成为活资产。效果：评测集首次能预测线上表现，回归拦截率【占位：__%】。
业界对比
BrowseComp（OpenAI）与 BFCL V3（UC Berkeley）是评测设计的两个参照系：前者学难度设计，后者学维度拆分。
设计巧思
评测集是公司的资产：它沉淀了“什么算对”的业务共识。

🔥 面试官深挖预演

追问 1
Q：评测集多大才够？
A：数量不如分布——分层覆盖（难度×类别×无答案）比堆量重要。BrowseComp 的“难找易验”原则：找难题的成本高，但验证答案便宜，出题预算花在刀刃上。
追问 2
Q：LLM-as-judge 靠谱吗？
A：是放大器不是真理：必须用人工金标校准一致率，错误样本回喂迭代。我们的 judge 校准到与人工九成一致才进流程，而且 judge 只用于抽检与回归，不用于发版门禁——门禁用确定性校验。

维度 9 · 冷启动与数据埋点：没有用户数据时怎么迭代

深挖维度
价值点：上线初期没有行为数据，优化无从下手——这是所有 toB AI 产品的共同困境。
① 问题定义
上线前两周的窘境：无点击数据、无负反馈，唯一信号是“客户没投诉”——而 toB 场景客户不投诉往往只是“懒得投诉”，弃用是静默的。问题定义：在自然行为数据积累起来之前，用什么信号驱动迭代优先级？空窗期持续越久，业务方耐心耗尽的风险越大。
② 问题分析
把信号来源拆成三档：能自动采集的（埋点事件：query、意图结果、检索命中、引用率、耗时）、能代理的（转人工率、复问率、会话放弃率——满意度的行为代理）、能主动要的（每周业务方评审会、灰度问卷）。关键认知：toB 的满意度不在点赞里，在“用户下次还来不来问”里——代理指标比直接反馈更真实。
③ 问题场景
现场：业务方反馈“感觉不太准”，追问哪里不准、什么场景、哪类问题——说不上来。没有数据，改进方向只能靠猜，工程资源砸错方向两周都是常事。这个“感觉不准”后来靠埋点定位到：条款版本混存导致的口径漂移，占比三成【占位：__%】。
④ 方案对比
方案优势劣势/风险结论
等自然积累，先不动零成本空窗期两三个月，业务耐心耗尽，项目风险最高否
全链路埋点 + 代理指标 + 主动评审空窗期也有信号；代理指标比问卷真实埋点设计要克制，否则噪音与成本失控采用
灰度问卷直接问用户直接toB 用户敷衍填，回收率与真实性双低否（作为辅助）
⑤ 采用与踩坑
采用：全链路事件埋点（从 query 进来到返回的每一步：意图结果、检索条数、rerank 分、生成耗时）+ 会话级点踩与原因勾选 + 每周“零引用答案清单”（无条款依据的回答人工复核）+ 业务方 badcase 评审会。踩坑一：埋点铺太全，日志成本与噪音齐涨——收敛到五类关键事件，其余按需加。踩坑二：点踩率极低（约 1%【占位：__%】）信号失真——引入复问率与放弃率交叉验证，单一信号不下结论。踩坑三：零引用清单人工复核量大——每周限量 + 按风险排序（涉数字、涉办理的优先）。
⑥ 验证与迭代
上线一个月积累【占位：__】条真实 query；识别出【占位：__】类系统性问题进入迭代；埋点数据与人工抽样判断做一致性校验，代理指标与业务方主观评价做相关性回测——指标可信才有资格驱动迭代。
业界对比
行业共识：智能客服解决率 90%+ 是标杆口径（平安/阳光），但“解决”的定义必须与业务方书面约定。

追问 1
Q：没有标注数据怎么做评测？
A：两条腿：探针集先行——先构造“我们必须答对”的题把底线守住；业务方评审会定性——真实分布慢慢进来。等数据攒够再建评测是最贵的选择，因为空窗期的方向错误没人纠正。
追问 2
Q：点踩率那么低，埋点还有意义吗？
A：有意义，但要换信号：toB 的真实负反馈是行为——复问（说明没答好）、放弃（说明没答到点）、转人工（说明不敢用）。点踩只是补充，行为代理才是主信号。

维度 10 · 上下文超限：提示词的压缩与裁剪

深挖维度
价值点：多轮对话 + 多证据引用必然撑爆窗口：压缩策略直接决定成本与质量。
① 问题定义
症状出现在第 8~10 轮：上下文超限，早期用最粗暴的滑动窗口截断——把最早的对话整段丢掉。事故现场：用户第 2 轮说“投保人按我老婆的信息算”，第 9 轮再问时模型按投保人本人口径回答——约束被截断了。定义为“多轮约束保持率”问题：第 N 轮仍能正确引用前文约束的比例。
② 问题分析
根因是信息没有优先级模型：改口、承诺、身份声明这类约束性信息，和寒暄、过程性描述在截断策略眼里是平等的——先来先扔。而约束信息的价值密度恰恰最高且不可再生（丢了用户不会重说）。次要因素：检索证据按条数截断而不是按相关度，导致后续轮次引用质量漂移。
③ 问题场景
复现场景：构造 20 组多轮会话（每组在第 2~3 轮埋入约束，第 8~12 轮验证），滑动窗口策略下约束丢失率过半【占位：__%】——用户视角就是“这 AI 失忆了”，而且是关键时刻失忆。
④ 方案对比
方案优势劣势/风险结论
滑动窗口截断实现零成本约束信息按时间被丢弃，关键信息恰恰在早期否
全量摘要替换历史窗口可控摘要本身有损且贵；约束在摘要中被稀释——“改成…”这类关键改口最容易被摘掉否
分级放置：状态区 + 滚动摘要 + 证据裁剪约束永不丢失；成本与质量平衡需要显式的信息分级逻辑，状态区要产品设计配合采用
⑤ 采用与踩坑
采用五级分级：系统规则（永不动）> 当前任务状态（必须保）> 近期对话（全保）> 早期对话（滚动摘要）> 检索证据（按相关度裁剪）。两个关键设计：约束类信息（“我刚才说的不算，改成…”）显式写入状态区，不参与摘要；检索证据按 rerank 分数装箱而非按条数截断，并做引用句柄化。踩坑一：摘要把“过程”摘掉了但把“结论与承诺”也稀释了——摘要模板强制保留结论、承诺、改口三类要素。踩坑二：摘要本身耗时耗钱——阈值触发（超限才摘要）+ 增量摘要（只摘新增段）。踩坑三：分级逻辑一开始埋在 prompt 里不可见——状态区做成显式结构（产品层可见“当前确认的信息”），反而成为信任感来源。
⑥ 验证与迭代
多轮一致性评测集（第 N 轮引用第 2 轮约束的通过率）+ 关键信息保留率人工评估；多轮约束保持率提升至【占位：__%】，单会话输入 token 下降约三成【占位：__%】。迭代：分级规则随 badcase 调整——每类丢失样本归因到“哪一级没接住”。
业界对比
LangGraph checkpoint / Manus 文件系统 / Mem0 记忆库是业界三种代表解法，对应“状态落库 / 句柄化 / 记忆蒸馏”。
设计巧思
压缩不是丢信息，是把信息分层放置：约束进状态区、过程进摘要、证据进句柄。

🔥 面试官深挖预演

追问 1
Q：为什么不直接上长上下文模型？
A：长窗口解决“放得下”，不解决“记得住”——lost-in-the-middle 实证：塞得越多中间信息利用率越低；且成本随轮次线性涨。分层放置是结构解，扩窗口是容量解，结构解不依赖模型升级。
追问 2
Q：状态区谁维护？模型自己写靠谱吗？
A：约束识别用模型（它擅长），写入与失效用确定性逻辑（版本化、可审计）——又是“模型理解、规则决定”的同款分工。状态区对用户可见，错了会被发现，可检测性保住了。

异常处理 Case 集（高频拷打）

异常 case：工具调用失败（佣金接口 5xx/超时）
重试分级：接口超时 3s 重试 1 次（幂等查询）；仍失败则降级为'系统繁忙，已记录，稍后回复'并生成待办工单——绝不编造数字。业务上把'如实说拿不到'定义成正确行为。
异常 case：实体解析失败（用户说'把我那份保单改了'但命中多张保单）
不猜。反问澄清：列出候选保单让用户选择；单保单但变更项模糊时给'你想变更哪一项'菜单。原则：办理类动作宁可多一轮澄清。
异常 case：工具循环调用（A 工具结果触发再调 A）
状态机防环：同一工具同参数连续调用计数，超 2 次强制跳出并转人工/澄清；步数预算上限 12 步。
异常 case：LLM 输出不合法 JSON（抽取失败）
schema 校验失败 → 带错误信息重试一次（把校验错误回喂）→ 再失败走澄清追问模板；绝不静默吞掉，因为下游规则引擎需要合法入参。
异常 case：检索空结果
三级降级：①放宽（同义改写/去掉产品限定词）重检 ②跨库检索 ③仍空则明确拒答'知识库暂未覆盖'并转人工，同时记录为知识缺口需求。
异常 case：拒答被业务方投诉'太保守'
阈值分层与数据化：按意图与风险等级配不同阈值，每季度用人工标注校准'该答未答/不该答乱答'的混淆矩阵。
