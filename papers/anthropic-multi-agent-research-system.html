How We Built Our Multi-Agent Research System

机构 / 作者Anthropic
时间 / 形式2025.06 · 工程实战复盘
链接原文
简历关联AI 应用平台 R2/R3 团队管理

总 · 解决什么问题

研究型任务串行执行慢、覆盖窄；单 agent 上下文装不下多源信息。

总 · 主旨思路与设计理念

orchestrator-worker：LeadAgent 拆解并行分派 subagent；状态增量保存；用 token 买广度。

一图看懂 · 核心机制

分 · 核心要点

  • 架构：LeadAgent 负责拆解与编排，多个并行 Subagent 各自带独立上下文与工具，最后汇总——适合'广度优先、可并行'的研究型任务。
  • 工程要点：任务描述要显式传递目标/输出格式/工具边界；按问题复杂度分配并行度；LeadAgent 像管理者一样给 subagent 写清楚任务说明书。
  • 可靠性优先：增量保存状态支持断点恢复、渐进式披露降低全量失败率；多智能体的调试难度远高于单链路。

分 · 关键数据与影响力

  • 内部评测中多智能体系统较单智能体 Opus 提升 90.2%（研究广度任务）。
  • 关键洞察：token 用量解释了 80% 的性能方差；多智能体用量约为普通聊天的 15 倍——收益换成本，只在值钱的任务上用。
  • 生产数据：多智能体在代码性、并行性强的任务上优势最大，串行依赖任务上可能为负收益。

总 · 一句话总结

多智能体的工业级样板，附完整成本账（90.2% 提升 / 15× token / 80% 方差）。

与简历项目的关联

  • AI 应用平台：自己在多轮对话里做摘要压缩控制 token——这篇给了行业级数据（15× token / 80% 方差），可引用说明成本工程是 agent 产品生死线。
  • R2/R3：多智能体并行 subagent 对基础设施的并发与延迟要求，正好接上你 10× QPS、流量整形的功底。
  • 团队管理：LeadAgent 写任务说明书 ↔ 你管理 17 人团队的任务分发经验，人机组织同构。

面试怎么结合

场景①'要不要上多智能体'｜回答：用 90.2%/15×token 这组数据说明它是'用成本买广度'，我的场景（知识问答）串行度高，暂不上；若做深度研究类功能则首选该架构。
场景②'多智能体最难的是什么'｜回答：调试与状态管理——Anthropic 也承认失败恢复最难，我的做法对应他们的状态增量保存。

实战复盘 · 🟡 半实战（Case 2 为方案设计与原型验证阶段）

Struggle
投研类问题——“某行业近三年竞争格局”——单轮 RAG 只能召回碎片，串行检索又慢又漏，分析师要人工开十几个窗口拼信息。
问题拆解
把研究问题拆成子问题 DAG（市场规模 / 玩家份额 / 竞争壁垒 / 近期事件），每个子问题绑定数据源与工具；确认子问题间可并行度。
调研与测试
对照 Anthropic 多智能体复盘的三个数字（+90.2% / 15× token / token 解释 80% 方差）做成本收益账；用三类真实研究问题做并行 vs 串行原型对比（耗时 / 覆盖率 / 冲突率）。
解决步骤
① 规划器拆解子问题 ② 多数据源并行取数（并发控制、超时降级、部分失败标注缺口）③ 证据治理（去重 / 口径对齐 / 打分）④ 交叉校验（数字双源一致）⑤ 分节生成带引用报告。
验证思路
fact 层：数字类结论双源一致率；report 层：rubric（结构完整 / 观点有据 / 口径一致）+ 人工基线对比。
达成效果
报告初稿从人工数小时缩短到分钟级【占位：实测数据】；诚实边界：方案与原型验证完成，未全量上线。
