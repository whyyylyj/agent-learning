EDD 评估驱动开发：学习目录

它是什么：EDD 把"评估"从开发流程的最后一步提到最前面——评估集就是需求规格（working specification）：先定义"什么算对"（golden set + 验收口径），再迭代系统，每次变更跑评估防回归。对标 TDD（测试驱动开发），但评的是生成质量而不是单元逻辑。
为什么对你重要：你的两个实战案例（意图分层评测集、勾稽校验、BrowseComp"难找易验"评测设计）本质上就是 EDD 的实践——这一页把这些散落的实践串成一个可以系统讲述的方法论，是面试里"你怎么保证质量"这类问题的理论背书。

学习路径（建议 5 天，每天 60–90 分钟）

天内容自测标准
D1建立直觉：Hamel《Your AI Product Needs Evals》+ Eugene Yan《Product Evals in Three Simple Steps》能复述"错误分析先行、评估集是资产"的核心主张
D2系统框架：Chip Huyen《AI Engineering》第 3 章（评估方法论）+ 第 4 章（推理与成本关联）能画出"基准→指标→评估方法"三层地图
D3学术严谨性：EDD 过程模型论文（2411.07781）+ EDDOps（2411.13768）能讲清 EDD 与 TDD 的异同、离线/在线评估闭环
D4动手工具：DeepEval（pytest 风格）或 Braintrust/Langfuse 之一跑通最小闭环给自己的一个真实链路写出 10 条 golden case + 3 种评分器
D5进阶与前沿：LLM-as-judge 综述 + Anthropic evals 工程实践 + 错误分析方法论（open/axial coding）能设计一个"分类别幻觉率门禁"方案并说出 judge 校准方法

一、奠基博客（先读，建立工程直觉）

资料作者/来源核心内容 · 为什么读
Your AI Product Needs EvalsHamel HusainEDD 的"开山"博客。真实房产 AI 助手案例：不看日志凭感觉迭代 = 瞎子摸象；用错误分析（看 300+ 条真实数据、open coding 归类失败模式）决定该建什么评估。读它建立"评估集是资产、域专用"的世界观。
Product Evals in Three Simple StepsEugene Yan最小可行动作：①标小数据集（20~50 条）②对齐 LLM 评估器（与人工一致率）③每次变更跑评估 harness。适合作为"今天就能做"的起步模板。
Error Analysis 系列与方法论（配套：AI Evals 课程笔记）Shreya Shankar / Hamel错误分析的操作细节：notebook 里逐条看 trace、open coding（贴标签）→ axial coding（聚合出失败模式）；"先看数据再定指标"反直觉但正确——大多数团队指标失效就是因为跳过了这步。
Evals for AI AgentsEugene Yanagent 形态的评估特化：多步轨迹怎么评（终态 vs 过程）、工具调用正确性、以及"评估要跟着能力走"的分层思路。与你知识库里 BFCL V3 / MAST 的视角互补。

六、与你知识库的勾连（面试复用）

EDD 概念你的实战对应
评估集是资产 / working specification第 4 章 评测体系 + 案例一维度 8：分层 golden set + 验收口径书面化 + dev/holdout 双集
错误分析先行（open/axial coding）案例一维度 7：幻觉 100 条人工归类四类来源，按占比定治理优先级——就是 open coding
评估先于迭代（防回归）发版门禁由人审改为数据审；跨库污染率、勾稽一致率纳入回归
LLM-as-judge 校准案例一维度 7：judge 与人工一致率七成→九成才进流程
在线评估闭环（EDDOps）案例一维度 9 埋点冷启动：转人工率/复问率/放弃率作代理指标 + badcase 回流
agent 分级评估案例二维度 10：fact 层（勾稽 verifier）+ report 层（rubric）双层评估 → 未来 RL 奖励基建
难找易验 / irrelevance⑰ BrowseComp（难度设计）+ ⑲ BFCL V3（该拒的拒）
面试一句话（把方法论收进口袋）："EDD 的核心是把评估从验收工具变成需求规格——先看数据做错误分析定出失败模式，再建域专用评估集和验收口径，每次变更跑回归防退化，上线后在线评估回流迭代。我的两个项目都是这个循环：案例一靠它把幻觉率从不可知变成分类别门禁，案例二的勾稽一致率就是天然的 verifier 评估。"
