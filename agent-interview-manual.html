Agent 设计面试学习手册

原创整理 · 面向后端/AI 应用工程师面试 · 结合保险 SaaS 场景与个人项目经历 · 2026-09

0 · 使用指南

这份手册按「概念 → 模式 → 工程 → 问答 → 场景」组织，建议三遍学习法：

  1. 第一遍（通读）：建立整体框架，每节记住一句话总结（已加粗在各节开头）。
  2. 第二遍（背答）：只看第 4 章面试题库，先自己答，再对照要点，答不出的回对应章节。
  3. 第三遍（串讲）：面试前一天，只看每节的「一句话总结」+「面试怎么答」卡片，用自己的话口头复述一遍。

核心心法面试官考察 Agent 设计，本质考察三件事：你会不会拆解需求到架构、你知不知道每个模式的适用边界和代价、你有没有真实落地的坑点经验。答概念时永远带上「适用场景 + 反例 + 我踩过的坑」。

1 · Agent 核心概念

1.1 Agent vs Workflow：一句话分清

一句话总结：Workflow 是开发者预先写死流程图，LLM 在固定节点里干活；Agent 是 LLM 自己决定下一步做什么、用哪个工具、何时结束。

维度Workflow（工作流）Agent（智能体）
控制流代码写死，确定性LLM 动态规划，概率性
可预测性高，易测试低，需评估与护栏
成本/延迟低（可小模型、可并行）高（多轮大模型循环）
适用任务步骤固定可枚举开放域、步数不可预知
失败模式节点内模型出错死循环、幻觉调用、跑偏

业界（Anthropic《Building Effective Agents》）的经典建议：能用 Workflow 不要上 Agent——从最简单的方案开始，只在任务确实需要灵活性时才引入自主性。面试时先说这句，展示工程判断力。

1.2 五大 Workflow 模式（必背，附一句话场景）

模式结构典型场景面试一句话
Prompt Chaining
提示链		 生成→校验→改写 生成营销文案后先过合规检查再润色 用延迟换质量，每个环节单一职责
Routing
路由分流		 分类器→分支A/B/C 客服咨询按「咨询/投诉/办理」分发不同提示与模型 简单问题走小模型，难题走大模型，省钱且降延迟
Parallelization
并行		 切分⇉并行处理→聚合 一份长合同同时做条款提取 + 风险审查 + 摘要 独立子任务并行降延迟；或同一任务多版本投票提质量
Orchestrator-Workers
编排者-工人		 编排LLM→动态拆子任务×N→汇总 多文件代码修改，编排者决定改哪些文件、分给谁 与并行的区别：子任务数量和内容由 LLM 运行时动态决定
Evaluator-Optimizer
评估-优化循环		 生成⇄评估→达标输出 翻译 → 评估员打分不合格 → 带反馈重译 有明确评分标准且 LLM 能给出有用反馈时才值得用

1.3 何时用 Agent：三条判断标准

一句话总结：任务的「路径不可预测」+「需要多轮工具交互」+「错误可恢复」时，才用 Agent。

  • 路径可预测吗？「查保单余额」固定两步 → Workflow；「排查这份理赔为什么被拒」步数不定 → Agent。
  • 需要模型自己组合工具吗？工具调用顺序固定 → 代码编排更好。
  • 失败的代价可控吗？Agent 会犯错，必须配护栏（工具白名单、金额上限、人工确认）。
面试加分点：主动说「生产环境 80% 的 AI 功能应该用 Workflow 实现，Agent 只用于长尾开放任务，且必须加循环上限（如最多 10 轮）和预算上限」。

2 · 八大核心设计模式

2.1 ReAct：推理与行动交替循环

一句话总结：让模型以「思考 → 行动 → 观察」的循环工作，把推理过程显式化，每步都基于最新观察修正方向。

Thought: 用户问保单状态，我需要先查保单系统
Action: query_policy(policy_no="P12345")
Observation: {"status": "active", "premium_due": "2026-10-15"}
Thought: 已拿到状态，还需确认是否有未决理赔
Action: query_claim(policy_no="P12345")
Observation: []
Thought: 信息足够，可以回答了
Final Answer: 您的保单状态有效，下一期保费 2026-10-15 到期，名下无未决理赔。
  • 实现要点：系统提示里定义 Thought/Action/Observation 格式；工具结果作为 Observation 追加进上下文；解析到 Final Answer 或达到轮数上限则停止。
  • 常见坑：① 不设轮数上限导致死循环烧钱；② Observation 太长撑爆上下文（要做工具结果裁剪）；③ 模型把 Observation 当成可编辑内容（用结构化分隔符隔离）。
  • 进阶变体：现代实现（如 Claude Code、OpenAI Assistants）已把「Thought」内化为原生 tool-use 消息格式，不再依赖文本协议解析——这是加分细节。
面试怎么答：先画循环（模型输出工具调用 → 执行 → 结果回填 → 再调模型），再说三个工程细节（轮数上限、观察值裁剪、工具调用解析的容错——模型输出不合法 JSON 时重试或降级），最后补一句「生产上我用原生 function calling 而不是文本协议，稳定性好得多」。

2.2 Plan-and-Execute：先规划再执行

一句话总结：先让强模型一次性生成完整计划（任务清单），再逐步执行，复杂任务比逐步 ReAct 更省 token、更可控。

  • 与 ReAct 的区别：ReAct 是「走一步看一步」，容易在长任务中迷失；Plan-and-Execute 先出全景计划，执行器按计划逐步完成，计划可随执行结果动态修订（re-plan）。
  • 适用边界：任务步骤多、子任务相对独立时收益大；简单任务反而增加一次 LLM 调用的开销。
  • 工程细节：计划要输出结构化格式（JSON 任务列表，含依赖关系）；执行中失败要区分「可重试」「需重规划」「直接终止」三种情况。

2.3 Reflection：自我反思与批判

一句话总结：让另一个 LLM（或同模型换视角）扮演评审员，对产出做批判性检查并给出修改建议，循环到达标为止。

  • 三种形态：① 单次自我检查（生成后追加「检查你的答案」）；② Reflexion（把失败反思存入记忆，下次尝试时带上）；③ 独立评审员角色（更客观，避免自我肯定偏差）。
  • 适用条件：有明确可评估的标准时才有效（代码能跑通、答案有依据）；开放式创作任务反思收益低。
  • 成本意识：每轮反思 ≈ 双倍 token，要在质量收益和成本间权衡，可只对高风险输出启用。

2.4 工具调用 Function Calling

一句话总结：把工具的名称、用途、参数 JSON Schema 声明给模型，模型输出结构化调用请求，由应用侧执行后把结果回填——模型只「点菜」，应用「做菜」。

  • 工具定义三要素：清晰的名称（动词+宾语）、精确的 description（模型靠它判断何时用）、带类型/枚举/必填标记的参数 Schema。
  • 工程五要点：
    1. 工具数量控制：超过 20 个工具模型选择准确率明显下降，按场景动态挂载子集；
    2. 参数校验：模型输出可能不合法，执行前必须 JSON Schema 校验，失败把校验错误回传让模型自纠；
    3. 幂等与权限：写操作工具要幂等设计 + 权限白名单 + 危险操作二次确认；
    4. 错误即信息：工具报错不要吞掉，把错误信息回传模型，它通常能自行修正参数重试；
    5. 并行调用：现代模型支持一次输出多个独立工具调用，注意并发执行 + 汇总回填。
  • 结果回填技巧：大结果（如整页检索文档）先裁剪/摘要再回填；敏感字段脱敏后回填。
面试怎么答：结合自己经历——「我在项目里封装过 20+ 内部 API 给 Agent 调用，踩过的最大坑是工具描述写得太含糊导致选错工具，后来统一了描述模板（用途+前置条件+返回结构+错误码），并给同类工具加了 disambiguation 提示，选择准确率明显提升。」

2.5 MCP：Model Context Protocol

一句话总结：MCP 是工具/资源接入大模型的开放标准协议（JSON-RPC 2.0），把「M×N 的集成问题」变成「M+N」，是 Agent 生态的 USB 接口。

  • 三种能力：Tools（模型可调用）、Resources（可读取的数据上下文）、Prompts（预置提示模板）；传输支持 stdio（本地进程）与 Streamable HTTP（远程服务）。
  • 架构角色：MCP Host（如 Claude Code）、MCP Client（Host 内的协议连接器）、MCP Server（暴露能力的轻量服务）。
  • 对比自研工具网关：MCP 的价值在标准化与生态复用——工具只需实现一次 Server，所有支持 MCP 的 Host 都能用；代价是多一层协议开销。
面试怎么答：被问「为什么需要 MCP，直接 function calling 不行吗」时答：function calling 是「模型怎么调用工具」的模型侧标准，MCP 是「工具从哪来、如何被分发接入」的生态侧标准，两者互补——一个解决调用格式，一个解决工具的分发、发现与复用。

2.6 RAG：检索增强生成

一句话总结：先检索相关知识再生成回答，用外部知识弥补模型参数里没有/过时/私有的信息，同时提供可溯源的引用。

标准流水线（六步，能画出来就赢）：

文档解析→ 智能分块→ 向量化入索引→ Query 改写→ 混合检索+Rerank→ 拼 Prompt 生成
  • 分块（Chunking）：非固定长度切分，按文档结构（标题/段落/表格边界）语义分块，块间保留重叠与层级元数据（所属章节）；表格、代码特殊处理。
  • 混合检索：向量相似度（语义）+ BM25 关键词（精确词、编号、专有名词）融合排序（如 RRF），再用 Cross-Encoder Rerank 精排 top-k——这两步通常能把召回准确率拉高一大截。
  • Query 改写：用户口语化提问与文档措辞不一致 → 用 LLM 改写/扩展/拆解查询（多轮对话还要做指代消解：「它的保费」→「XX产品的保费」）。
  • 评估指标：检索侧 Recall@k / MRR；生成侧 Faithfulness（忠实度，防幻觉）、Answer Relevance。工具：RAGAS 等。
  • 高阶：知识库实时性用「增量索引 + 缓存失效策略」；复杂问题用「多跳检索」（先查 A 再用 A 的结果查 B）；表格类问题考虑 Text-to-SQL 补充。
面试怎么答（结合简历）：「我为保险公司做过条款知识库，准确率 90%+。三个关键决策：① 语义感知分块替代固定长度，保住条款结构边界；② 向量+BM25 混合检索解决条款编号查不到的问题；③ Rerank 精排 + Query 改写解决口语与条款措辞不一致。评估上用标注测试集做自动回归，每次改参数跑一遍防退化。」——这就是面试官想听的「有数据、有决策、有闭环」。

2.7 记忆系统：短期与长期

一句话总结：短期记忆 = 上下文窗口管理（塞得下、留重点），长期记忆 = 外部存储（向量库/数据库），按需检索回来。

  • 短期（上下文内）：滑动窗口截断、摘要压缩（长对话把早期轮次压缩成摘要，保留关键事实）、结构化状态抽取（把对话沉淀成 JSON 字段而非堆原文）。
  • 长期（外部存储）：用户画像/偏好 → 结构化库；历史对话/事实 → 向量库按语义召回；写入时机要判「值得记吗」（用户明确表达的偏好才记，避免噪音）。
  • 多轮对话三大坑：指代消解（“它”指什么）、上下文丢失（早期约束被截断）、Token 成本随轮次线性涨 → 对应解法：改写消解、关键事实外置、摘要压缩。
面试怎么答（结合简历）：「我做的场景模拟培训问答里，长对话用摘要压缩控制 Token 消耗：超过阈值触发压缩，把前 N 轮压成结构化摘要（已确认的事实、未决问题、用户偏好），并保留最近 2 轮原文——既保住关键信息又把 Token 增长从线性降为准常数。」

2.8 Multi-Agent：多智能体协作

一句话总结：把复杂任务拆给多个各有专长/工具/上下文的 Agent 协作，本质是用「关注点分离」换「单上下文的纯净度」——代价是通信与一致性复杂度。

  • 四种常见拓扑：
    1. 编排者-工人：一个主 Agent 拆任务分派、汇总（最常用、最稳）；
    2. 流水线：A 的产出是 B 的输入（如 需求→编码→评审→测试）；
    3. 辩论/评审：多 Agent 各自作答再互评收敛（提升严谨任务质量）；
    4. 群体 chat：共享群聊上下文自由协作（灵活但易失控）。
  • 什么时候真的需要多 Agent：① 单上下文塞不下（各子任务需要各自的大量专属上下文）；② 需要不同模型/不同工具权限（如只读 Agent + 可写 Agent 分离）；③ 子任务可并行。
  • 通信设计三选一：共享完整对话历史（省事但上下文污染）、结构化消息（推荐：只传任务描述+产出）、共享黑板/状态库。
  • 必答的坑：级联误差放大（上游错下游全错）、成本倍增、调试困难（需要全链路 trace）、死循环互踢皮球 → 靠「明确契约 + 轮数上限 + 全链路可观测」治理。
量化证据：这个「泼冷水」立场有实证支持——Google 2025 年底用 180 组控制变量实验定量证明了多 Agent 收益取决于架构-任务匹配而非 Agent 数量，三大效应详见 第 7 章论文精读。面试中引用这篇论文 = 免费的深度加分。
面试怎么答：先泼冷水再给方案——「我不倾向为了多 Agent 而多 Agent。判断标准是上下文是否需要隔离：比如保险理赔场景，核保规则查询和理赔材料审核需要的工具与提示完全不同，拆成两个专职 Agent（各自单一职责 + 独立评估）比一个大而全的 Agent 可维护得多。编排上我用编排者-工人模式，消息传结构化任务单而不是堆聊天记录。」

2.9 Guardrails：护栏与安全

一句话总结：在 Agent 的输入、决策、输出、执行四个环节都设检查点，假设模型一定会犯错，用工程手段把损失框住。

  • 输入侧：Prompt 注入检测（用户输入中夹带指令试图劫持 Agent）、敏感信息过滤、话题边界校验。
  • 决策侧：工具调用白名单、参数范围校验（金额上限）、危险操作分级（只读直接执行 / 低危静默 / 高危人工确认 human-in-the-loop）。
  • 输出侧：格式校验（JSON Schema）、事实性抽检（引用是否存在）、合规审查（保险行业的话术合规）。
  • 执行侧：预算与轮数上限、幂等与回滚、全量审计日志。
保险行业必答点：涉及保费计算、理赔金额、条款解释的输出必须「AI 给建议 + 规则引擎复核 + 人工终审」，且话术要符合监管要求——这是体现行业理解的加分项。

3 · 工程落地

3.1 上下文工程 Context Engineering

一句话总结：Prompt 工程的升级版——不只是写好一句提示，而是系统化地决定「每一轮该把什么信息放进有限上下文」：系统规则、工具定义、检索内容、对话历史、记忆，全是预算内的稀缺资源。

  • 优先级排序：系统规则 > 当前任务必需信息 > 相关检索结果 > 摘要历史 > 完整历史——超预算时从后往前砍。
  • 技巧：关键约束放开头结尾（中间注意力弱，"lost in the middle"）；结构化分隔（XML/Markdown 区块）比自然语言堆砌好；工具结果先裁剪再入上下文。
  • 结合简历：「我沉淀过团队级的上下文模板：角色定义 → 领域规则 → 输出格式示例 → 当前任务 → 参考材料，新场景只改领域块，A/B 验证后全量。」

3.2 可观测性

一句话总结：Agent 是概率系统，没有 trace 等于盲飞——每一次 LLM 调用、工具调用、耗时、token 数都要留痕可回放。

  • 三层追踪：会话级（session）→ 运行级（一次 agent run 的完整轨迹树）→ 调用级（单次 LLM/工具调用）。
  • 关键指标：任务成功率、平均轮数、工具调用错误率、每会话 token 成本、P95 延迟、人工接管率。
  • 工具：LangSmith / Langfuse / OpenTelemetry（自建）。

3.4 评估体系（Agent 最难也最值钱的部分）

一句话总结：Agent 改一行提示可能引发连锁退化，没有自动评估闭环就等于裸奔——「标准测试集 + 自动评估 + A/B 灰度」是_agent 应用的 CI/CD_。

  • 评估三层：
    1. 单点评估：单次 LLM 输出质量（准确性/格式/合规），可规则可 LLM-as-judge；
    2. 轨迹评估：Agent 的完整路径对不对——工具选得对吗？顺序合理吗？步数是否冗余？
    3. 端到端评估：任务最终完成率（用真实/模拟用户任务集跑批）。
  • LLM-as-judge 要点：评分维度拆细（每维 1-5 分 + 理由）、给 few-shot 评分锚点、位置偏差用交换顺序消除、定期用人工标注校准 judge。
  • 闭环流程：线上坏例 → 沉淀进测试集 → 改进提示/检索 → 自动评估对比 → 灰度 → 全量。结合简历：「我的 Prompt 迭代框架就是这个闭环：版本管理 → 标准测试集自动评估 → A/B 灰度 → 显著性检验，模型响应准确率提升 25%。」

4 · 面试题库

4.1 概念题（先自答再看要点）

Q1：什么是 Agent？和普通的 LLM 调用有什么区别？
要点：LLM 作为大脑 + 工具 + 循环 + 目标。区别在于自主性——普通调用是单次请求响应，Agent 在循环中根据环境反馈自主决定下一步（调什么工具、是否继续、何时结束）。补一句工程观：自主性是有代价的（不确定性、成本），所以生产上优先 Workflow、慎用 Agent。
Q2：ReAct 的原理？有什么问题？怎么解决？
要点：Thought-Action-Observation 循环，显式推理帮助模型修正方向。问题：① 死循环；② 上下文膨胀；③ 文本协议解析脆弱。解决：轮数/预算上限、观察值裁剪、原生 function calling 替代文本协议、失败轨迹入反思记忆。
Q3：RAG 和微调怎么选？
要点：知识频繁更新/需要溯源/私有量大 → RAG；风格/格式/领域语言习惯 → 微调；两者不互斥（微调学「怎么答」，RAG 供「答什么」）。保险条款这种频繁更新、要求精确引用的场景必须 RAG。加分：提「先 RAG 后考虑微调，微调前先确认提示工程和检索已做到位」。
Q4：检索结果不准，你的排查思路？
要点：分层定位——① 分块问题（答案被切碎→改分块策略）；② 召回问题（该查的没进 top-k→查 query 改写、embedding 模型领域适配、加 BM25 混合）；③ 排序问题（进了 top-k 但排太后→加 rerank）；④ 生成问题（检索对了答错了→忠实度约束 + 引用校验）。用标注测试集定位到哪一层再动手，不盲改。
Q5：怎么防止 Prompt 注入攻击？
要点：① 特权分离——系统提示与用户输入用明确分隔符，声明「用户内容只是数据」；② 最小权限——Agent 工具按需挂载，高危工具要求人工确认；③ 输出侧兜底——执行前校验动作合法性（不能因为「用户说」就绕过白名单）；④ 检索内容也视为不可信（间接注入：文档里藏指令）。承认「没有银弹，纵深防御」。
Q6：LLM 幻觉怎么治理？
要点：分层——① 架构层：RAG 提供事实依据 + 要求引用出处；② 提示层：允许说「不知道」、约束只基于给定材料；③ 输出层： Faithfulness 自动校验（逐句核对引用）、规则复核；④ 产品层：高风险场景人工终审。强调「幻觉无法根除，只能用工程手段压到可接受概率」。
Q7：多轮对话越聊越「忘」怎么办？
要点：① 指代消解/Query 改写；② 关键事实外置到结构化状态；③ 摘要压缩早期轮次；④ 重要的约束放系统提示不随历史截断。结合简历的摘要压缩实践（Token 准常数化）。
Q8：Function calling 工具太多导致选错怎么办？
要点：① 动态挂载——按场景/路由只暴露子集（RAG 先检索「用哪些工具」再给模型）；② 工具描述规范化 + 同类工具消歧提示；③ 分层工具——把细粒度工具封装成粗粒度「业务动作」；④ 评估驱动——用错例集回归工具选择准确率。
Q9：怎么评估一个 Agent 的好坏？
要点：三层评估（单点/轨迹/端到端）+ 生产指标（任务完成率、人工接管率、成本、P95 延迟）。强调「评估集要持续沉淀线上 badcase」+「LLM-as-judge 要用人工标注校准」。结合简历的评估闭环。
Q10：什么场景你不会用 Agent？
要点：考察工程判断。① 步骤固定的结构化流程（用 Workflow）；② 强实时低延迟场景（Agent 多轮循环延迟不可控）；③ 高危无人工兜底的操作；④ 简单分类抽取（直接小模型单次调用）。答这题的核心是展示「克制」。

4.2 场景设计题（白板设计套路：澄清需求 → 总体架构 → 关键模式 → 风险与兜底）

设计题 1：给保险公司设计一个面向代理人的智能问答助手（条款/产品/核保规则）
答题框架：
① 澄清：用户是谁（代理人，专业但非系统内部）、问题类型分布、知识更新频率、合规要求。
② 架构：意图路由（产品咨询/核保规则/理赔流程/闲聊）→ RAG 主链路（条款知识库混合检索 + rerank）→ 生成（强制引用条款编号）→ 合规后处理。
③ 关键决策：核保规则类问题用「检索 + Text-to-SQL/规则引擎」混合，纯 RAG 算不准数字；知识库增量索引保证新品上线当日可查；低置信度时转人工并记录 badcase。
④ 风险：条款解释错误 → 强制引用 + 免责声明 + 抽检；Prompt 注入 → 输入过滤；违规话术 → 合规规则后审。
⑤ 评估：标注测试集 + Faithfulness + 转人工率监控。简历连接点：直接讲民生保险 RAG 知识库实践。
设计题 2：设计一个「投保单智能预审」Agent（自动检查材料完整性并给出初审意见）
要点：这是「Workflow 为主 + Agent 为辅」的典型——材料 OCR/抽取（固定流程）→ 完整性规则校验（规则引擎，不是 LLM）→ Agent 只负责「模糊地带判断 + 解释生成」（如材料内容与声明不一致的语义比对）。强调：能用规则的不用模型，模型的输出附证据链供人工复核，整个预审可追溯。
设计题 3：设计多 Agent 协作的「保单综合分析」系统（一个问题涉及条款+费率+理赔历史）
要点：编排者-工人模式——编排 Agent 拆解问题为子查询 → 三个专职工人（条款 Agent/费率 Agent/理赔历史 Agent，各自独立工具与上下文）→ 汇总 Agent 整合输出。讨论 trade-off：并行降延迟 vs 成本×3；结构化任务单通信 vs 共享上下文；失败降级策略（某个工人失败时汇总方明确声明信息缺失而非编造）。
设计题 4：客服 Agent 误答导致客诉，怎么做事故复盘和预防？
要点：考察 SRE 思维迁移到 Agent——① 止血：下线/降级该场景到人工；② 取证：trace 回放定位是检索错、生成幻觉还是工具错；③ 修复：badcase 入测试集 + 针对性修复；④ 验证：自动评估对比 + 灰度放量；⑤ 预防：该类问题加自动回归 + 输出加引用约束。加分：提到「分级放量 + 快速回滚机制」。
设计题 5：如何把现有单体应用逐步改造为带 AI 能力的平台（不推翻重来）？
要点：演进式架构思路——① 先加「旁路能力」：知识库/客服等独立新服务，不动核心；② 抽 AI 网关：统一模型接入、鉴权、计费、trace；③ 再改造核心流程中的单点（如用 LLM 替换某个规则解析模块，AB 验证）；④ 最后考虑 Agentic 化。结合自己「0→1 建 AI 平台 + 传统系统微服务化改造」的双重经历作答。

7.1 研究问题与实验设计（控制变量思想是最大亮点）

要解决的问题：业界流行「more agents is all you need」，但缺乏定量框架判断什么时候加 Agent 放大性能、什么时候放大错误。此前 MAS 评测的两大缺陷：① 混杂了提示/算力预算等实现差异，无法归因于架构本身；② 只看最终准确率，不看协调开销、误差传播等过程动态。

8.1 并发基础三连

Q1 · HashMap 和 ConcurrentHashMap 有什么区别？

HashMap 线程不安全，并发写会丢更新，JDK 7 还有扩容死循环的历史问题；ConcurrentHashMap 在现代 JDK 里用 CAS + 桶级 synchronized + volatile 语义实现高并发，读基本无锁。但更想强调一个生产上更容易出事的点：单次操作线程安全 ≠ 复合操作安全——get 完判断再 put，两步之间别人可能已经改了，必须用 putIfAbsent、computeIfAbsent 这类原子 API。

追问点（computeIfAbsent 的坑）：映射函数执行时会对该桶加锁——函数里做远程调用这类慢操作会把整个桶的并发都堵住，函数里抛异常或递归更新同一 map 也有奇怪行为。所以我的纪律：映射函数只做纯内存构造，慢操作放外面。

拉到架构层：这两者都只保护单进程内的状态。交易防重这种正确性问题，多实例部署下还是要靠数据库唯一约束和权威服务——进程内的并发结构再安全也替代不了分布式正确性。

亮点：「单次安全≠复合安全」+ 锁桶细节是生产踩坑才讲得出的；结尾升维到进程内 vs 分布式。

Q2 · volatile 能干什么、不能干什么？happens-before 讲一下

volatile 写保证对后续读可见，建立 volatile 写 → 读的 happens-before，并禁止指令重排跨过它；但 count++ 是读-改-写三步，volatile 管不了原子性，照样丢更新。适合场景是状态标志和安全发布（优雅关闭的 running 标志、配置引用发布）。

happens-before 挑最常用的说：程序次序规则、锁释放先于后续加锁、volatile 写先于读、线程 start/join 传递性。意义是给编译器和 CPU 的重排画红线——只要动作之间有 happens-before 边，JMM 就保证顺序和可见性；没有边的并发访问就可能出现反直觉结果。

落到业务：有人想用 volatile 做订单防重，直接否掉——服务是多实例的，进程内标记跨不过实例边界，正确性必须靠唯一约束/版本号/权威服务。并发工具解决的是性能和协作，不是正确性。

Q3 · synchronized 和 ReentrantLock 怎么选？讲讲 AQS

功能上：ReentrantLock 多了可中断、tryLock 超时、公平锁、多个 Condition；synchronized 胜在语法简单、自动释放、JDK 持续优化后性能不差。我的默认选择是 synchronized，只有明确需要中断/超时/条件队列时才上 Lock——Lock 忘了 finally unlock 就是生产事故。

AQS 是共同地基：一个 volatile int state + CLH 变体的双向等待队列。获取锁 = CAS 改 state，失败入队 park；释放唤醒后继。独占（ReentrantLock）、共享（Semaphore/CountDownLatch/读写锁）都在这套模板上定制 tryAcquire/tryRelease。它把「资源状态」和「线程排队」解耦，这是整个 JUC 包的设计中枢——读 AQS 源码最大的收获是这种「模板方法 + 等待队列」的框架设计思想。

老规矩补边界：都只管单 JVM，跨实例互斥是分布式锁的领域，而分布式锁也只是协调手段，正确性还是要唯一约束兜底。

亮点：给出明确默认选项不和稀泥；AQS 提炼为设计思想并可迁移。

8.2 线程池与并发实战

Q4 · 线程池怎么配？队列突然涨起来怎么排查？

配置上不背 CPU×2，那只是初始估计：CPU 密集偏 N+1，I/O 密集按等待比估，最终以压测为准。我真正在意的是四条纪律：① 队列必须有界（无界队列把过载转化为内存上涨和长尾延迟，等于把故障推迟并放大）；② 按下游隔离（调柜台、查行情、发消息各用各的池）；③ 拒绝策略匹配业务语义（下单被拒必须明确告知未受理，不能悄悄丢）；④ 任务带超时和上下文（traceId、用户上下文传递、可取消）。

队列上涨排查顺序：入口流量有没有突增（业务洪峰还是异常重试循环）→ 下游依赖耗时（某下游 P99 恶化拖慢处理）→ 线程被锁或 I/O 卡住（thread dump）→ 拒绝数和活跃线程。短期手段是限流/降级保实例，不是无脑加线程——加线程会把压力转移给已经慢了的下游。

CallerRunsPolicy 的反直觉点：Web 场景它等于让 Tomcat 线程亲自干任务，把过载直接传导回容器线程池把接口卡死。流量整形场景我宁可显式快速失败 + 入口限流。

Q5 · CompletableFuture 做资产聚合有哪些坑？

五个坑全是实操细节：① 默认线程池是公共 ForkJoinPool，要换成按下游隔离的执行器；② 单 future 超时 ≠ 总预算——四个子查询各 800ms 超时，串行感知 3.2 秒，正确做法是入口定总 deadline（如 800ms）向下分配子预算，到点收已完成的；③ 异常会被吞，exceptionally/whenComplete 每个子链路都要挂；④ 取消不终止底层 I/O，只是放弃等待，下游还在烧资源；⑤ ThreadLocal 上下文切线程丢失，MDC traceId、用户上下文要显式传递。

资产聚合页再加三条纪律：子查询结果带数据时点和完整性标记（「基金持仓：截至 xx:xx，正常」「信用账户：刷新中」）；失败模块显示降级提示而不是把缺失值当 0；资金持仓以权威系统为准、谨慎缓存。聚合接口的 P99 = 子调用 P99 的 max + 编排开销，优化要打在最慢那块板上。

Q6 · ThreadLocal 为什么会内存泄漏？线程池里还有什么风险？

结构：每个 Thread 里有 ThreadLocalMap，key 是弱引用、value 是强引用。线程长期存活（线程池正是如此），key 被 GC 后变 null，value 却顺着强引用链一直挂着——这就是泄漏。规范做法 finally { remove() }，线程池场景这不是建议而是必须。

线程池里更危险的是串数据：忘 remove 时下一个任务复用线程，可能读到上个任务的登录态/traceId——用户 A 的请求带上用户 B 的身份，是资金系统不可接受的事故级别问题。纪律：ThreadLocal 封装在统一上下文工具类，set/remove 成对；异步显式传递而非隐式继承（InheritableThreadLocal 在池化线程上语义还是错的）。

8.3 金融细节 + JVM 与线上排障

Q7 · 用了 BigDecimal 就不会算错钱吗？

至少四个坑：new BigDecimal(0.1) 把二进制浮点误差原样带进来，必须用字符串构造；除法不指定 scale 和 RoundingMode 直接抛 ArithmeticException；equals 同时比较数值和 scale（1.0 ≠ 1.00），比较用 compareTo；舍入规则必须由业务定义（HAL_UP 还是银行家舍入、手续费哪步取整——业务决策不是技术决策）。

更想说的是上一层：金额错误大部分不是 BigDecimal 用错，而是口径错——数据库 DECIMAL 精度、Java scale、接口字段、前端展示四处不一致；多币种都按两位小数处理；分摊逻辑最后一笔不「找零」加和就对不平。我的做法：内部金额统一最小单位整数或统一 scale，口径写成文档 + 性质测试（加总守恒、正负性、精度边界），BigDecimal 只是执行者。

Q8 · 线上 CPU 100%，你怎么定位？

先判断要不要立即止血：用户已受影响就先限流/回滚/摘实例，定位在止血后做；单实例异常就摘掉保留现场慢慢分析。

定位路径：① 区分用户态/内核态 CPU，排除容器限额和宿主机噪声；② top -Hp 找高 CPU 线程号转十六进制，到 jstack 对上 Java 栈，两三轮采样确认稳态热点；③ 更推荐 async-profiler 或 JFR 火焰图——看是业务代码、正则回溯、序列化/加解密、GC 线程还是锁自旋；④ 形成假设后找反证：正则回溯就构造输入复现，GC 就看日志频率与耗时占比。

我处理过的高频原因：正则回溯、大对象序列化（性能优化项目里把 20 秒指标计算优化到 100ms，其中一步就是换掉低效序列化——我还维护过 Apache Fury，对这块熟）、锁竞争自旋、GC 本身。修复后用修复前后吞吐、P99、CPU/请求三组数据证明有效，而不是「感觉快了」。对照：CPU 不高但接口慢，优先怀疑锁等待、下游 I/O、线程池排队、连接池耗尽。

Q9 · 内存持续上涨一定是泄漏吗？OOM 一定有 heap dump 吗？

不一定。缓存预热、业务 live set 自然增长、堆自适应伸缩都是正常上涨。判断锚点：Full GC 后的基线——每次 Full GC 后最低点在抬高且同比突增才可疑。

OOM 也不一定有 dump：HeapDumpOnOutOfMemoryError 没配、磁盘写不下、或 OOM 的根本不是 Java 堆——元空间（类加载器泄漏）、直接内存/堆外（Netty/NIO，维护 Fury 时对堆外序列化缓冲区这块比较敏感）、线程栈过多、本地库内存，都不在 heap dump 视野里，要用 pmap、NMT（NativeMemoryTracking）、jcmd VM.native_memory 和线程数排查。

确认堆内泄漏：heap dump 支配树看 Retained Size 最大的引用链，常见嫌疑是无界缓存（修复是加容量上限和淘汰，不是加堆）、监听器未注销、ThreadLocal。

Q10 · 接口 P99 突然升高，完整排查思路？

先确认三件事：影响面（一个接口还是全部？一个实例还是全部？）、时间线（和发布/流量/上游变更对不对得上）、成分（变慢的请求多了，还是尾部更慢了）。

把一次请求耗时拆开，P99 恶化一定藏在这些段里：总耗时 = 排队（容器/线程池/连接池）+ 应用计算（GC/序列化/热点）+ DB（慢SQL/锁等待）+ 缓存（穿透回源/热key）+ 下游 RPC（超时重试放大）+ 网络。用 trace 拉慢请求 span 对比正常样本，配合流量、错误率、GC、线程池指标形成假设再验证。

止血优先于根治：限流、降级、回滚、扩容都是止血；但止血后必须找根因——「扩容后好了」可能是流量回落的巧合。根治后压测验证、灰度放量，并把这类问题加进监控和预案。

Q11 · Young GC 频繁要不要调？怎么证明 GC 优化有效？

Young GC 频繁本身不一定有害——分配速率高时它就该频繁，关键看停顿占比和吞吐：每次 5ms、每秒 5 次才损耗 2.5%，业务无感就别动。出手的信号：停顿被拉长、晋升过快导致老年代异常增长、Full GC 出现。

定位：JFR 或分配画像找分配热点（开盘高峰的短生命周期 DTO、行情批次临时集合、JSON 反序列化中间对象）。优化顺序永远先减分配，再考虑调堆；调大 young 降频但拉长单次停顿，old 区调大推迟 Full GC 但让真泄漏更晚暴露——每个参数都有代价。

证明有效：同一压测模型下对比四组数——GC 频率与停顿占比、接口 P99/P999（GC 是长尾杀手，P999 比均值敏感）、吞吐、CPU/请求；并跑长稳确认没把问题转移（如大对象转进 old 区）。

9.2 决策日志 ① 保险条款 RAG 知识库

开场重构（放弃清单式开场，改用问题式）：不说「我做了分块、混合检索、rerank」，而说——

「这个项目最难的其实不是把准确率做上去，是让业务方相信这个准确率在真实问题里能维持。我先讲三个当时判断错的地方，再讲最终架构。」

决策 1 · 分块（第一次被打脸）：v1 用固定 512 token 滑窗（开源方案都这么写），内测暴露两类错——「犹豫期退保手续费」的答案横跨两块边界（比例在表格、条件在上一段）；引用错位说「根据第 3 条」实际在第 5 条，引用错一次，业务信任清零。候选对比：固定长度（切语义，否）／整篇一块（超上下文，否）／embedding 动态切分（阈值不稳计算贵，放弃）／结构感知分块（✓ 按标题层级+编号边界切，表格独立成块挂父章节）。采用后又踩坑：业务手写的 Word 标题不规范（「（三）」和「3.」混用），纯解析器不可靠 → 字号+编号模式+加粗三信号启发式 + 人工抽检脚本；表格切块携带表头和章节路径前缀元数据。

决策 2 · 混合检索（现象驱动）：纯向量时「XX 产品保险期间」召回的是语义相近的别的产品——产品名在 embedding 里被语义平滑，数字和专有名词是向量弱项；但全上 BM25 解决不了「交钱 vs 保费缴纳」的同义改写。融合用 RRF 而非加权分数——两路分数量纲不同，加权要调参且不稳，RRF 只用排名免归一化，不碰「权重调参」这个无底洞。

决策 3 · Rerank 与改写都「省着用」：rerank 本质是双塔→交互式的补偿，但每次请求对几十个候选各跑一遍 cross-encoder，有实打实延迟费用 → 简单事实题路由跳过。Query 改写本身有失真风险（可能丢掉用户真实意图），只对三类触发：带指代／口语化短查询／多条件复合。全量开改写在回归集上准确率反而降了——这个反直觉教训比框架值钱。

90% 的命门（必被追问）：标注回归集（业务真实 top 问题 + 标准答案 + 来源条款，约 300 条量级，双人背对背标注 + 争议仲裁 + badcase 月度增量）上「关键点命中且无事实错误」的比例；分层测：检索召回一个数、忠实度一个数、端到端 90% 是串联结果——准确率一降立刻知道是检索层还是生成层的问题。

事故还原：「犹豫期退保手续费」答错——条款 v2.1 上线后旧文档没下线，两版同时被召回，模型综合出不存在的数字。修复：文档版本管理 + 生效日期过滤 + 增量索引 + badcase 进回归集。教训：知识库的运维比算法难——算法决定上限，运维决定下限。

追问树（L1→L4）：90% 怎么测 → 为什么不微调（月更追不动/要溯源/微调教风格 RAG 供事实）→ 检索对答错怎么办（强制基于材料 + 引用回验 + 低置信转人工）→ 重做什么（条款要素结构化 + Text-to-SQL 混合，纯 RAG 对精确数字天然弱）。

9.3 决策日志 ② 分布式异步轮询框架

开场重构：不讲「我设计了一个框架」，讲——

「这个框架不是我想做架构，是两个改不动的物理约束逼出来的：公司网关 60 秒超时上限（基建，改不动）+ 浏览器同域 4-6 个并发连接限制（浏览器，改不动）。绩效报告一个十几张卡片每张一个轮询，用户一多 Tomcat 线程池打满全站卡。这两个约束讲清楚，方案是被推理出来的，不是背出来的。」

否决记录（表格化背下来）：

候选否决理由
WebSocket能力过剩（请求-响应场景用不到双向）；要动网关运维体系，团队没有集群化 WS 运维经验——组织约束也是真实理由
调大轮询间隔治标：连接占用没变，体验更差
MQ 推前端服务端到浏览器没有 MQ 通道，绕一圈还是轮询，本质没解
Servlet 3.1 异步 + Redis pub/sub 长轮询✓ 复用全部 HTTP 基建，连接数从「用户×卡片」降到「用户×1」

为什么参考 Nacos 2.0：配置中心是同构问题（客户端及时感知服务端变更）——读它的演进（1.x UDP/长轮询 → 2.0 gRPC 长连接）学到的不是协议是「订阅机制 + 超时兜底 + 增量合并」三件套。好架构师不是发明方案，是识别同构问题再移植。

三个坑各对应一条防御性设计：① pub/sub 丢消息 → 消息只传「有更新」信号不传数据，收到信号查结果库，丢信号靠超时兜底——假定它会丢，不给它加不属于自己的职责；② AsyncContext 句柄泄漏（客户端提前断开）→ 超时强制 complete + 错误回调注册；③ 回写线程池与业务池隔离。

数字的表态：10 倍 QPS 是同一台压测机同一份数据集下测的——「具体数字我可以翻压测报告」比背一个数可信得多。

追问树：为什么不用 DeferredResult（底层同源，用原生是为了统一管理订阅/超时/断开三类生命周期；今天重做会选 SpringMVC 封装）→ pub/sub 为什么不用 Stream/MQ（信号不可丢才需要 ACK/消费组，我们不需要为信号付出这些复杂度）→ 挂起连接上限（占的是轻量等待资源非工作线程，内存/句柄估算 + 网关限流双保险）→ 今天重做（SSE + HTTP/2 候选；不变的是超时兜底和线程池隔离）。

9.4 决策日志 ③ 跑批优化 12h→3h

叙事起点：第一步不是优化是测量——给每个指标计算埋点统计调用量与耗时分布，帕累托画出 60% 调用是净值静态类计算但占执行时间大头。再读运行机制：Celery 生产者消费者，每次调用要序列化完整净值序列过网络——瓶颈根本不在计算，在传输（八成时间在序列化/网络 IO/排队）。

否决记录：优化 Celery 批量接口（试过——批量只省调度开销，传输才是大头，治标）／Python 直算 + 文件交换（隔离还在，文件协议一致性复杂）／高频静态计算 Java SDK 化（✓ 网络 0 序列化 0，代价是双语言维护）／全量重写（低收益的动态建模类不动，避免不必要战场）。

精度对齐（最动人的细节）：为什么 1e-5——界面显示 2 位但年化复利链路会把中间误差放大到可见位。自动化双跑框架：同一输入双跑 Python/Java 逐指标 diff，跑历史全年数据，真找出三处不同（浮点求和顺序、四舍五入时点、复利公式约简差异）才敢灰度。这个对齐框架后来成了团队换计算引擎的标准流程。

组织面：计算是 Python 团队的地盘，处理方式是「按计算特征重新划界」而非「谁取代谁」——净值静态类归 Java SDK（确定性计算），持仓动态建模归 Python（专业量化逻辑）。这个分工到今天还在用——方案活下来了，是比 12h→3h 更踏实的证据。第二个隐性收益：省出的算力直接支撑用户量翻倍没扩容。L5：今天重做会先试增量计算 + Arrow 列式批处理，但「先测量、按特征划界、精度双跑门禁」三条方法论不变。

9.5 真实化清单（面试前必做）

  4. Prompt：测试集真实规模；显著性检验当时是真做了还是只做了简单对比（没做过就大方说，换成你真实的评估踩坑）
  5. 所有带「示例」标记的数字全部过一遍

三条原则：① 宁可数字小，不可数字虚（120 条但每条讲得出标注故事，比虚报 500 条可信十倍）；② 没做过的环节大方承认（「当时是单人标注加抽检」是完全合格的答案，编造才会崩）；③ 每个细节准备「下一层」——准备不了的细节不要主动讲。

使用节奏：面试前一周完成核对替换 → 按五层把四个项目各口头讲一遍（录音回听）→ 找人模拟追问树（每项目至少打到 L3）→ 面试前一天只过「亮点」和「避坑」。
